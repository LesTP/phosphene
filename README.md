# Phosphene

*Light that originates from within*

## What This Is

A phosphene is light perceived without light entering the eye — generated by the visual system's own structure rather than by an external source. The name captures what this project is attempting: a system that produces something that appears to come from outside but originates entirely in its own accumulated structure.

Phosphene is an autonomous agent seeded with a human's writing corpus and structured to develop a personality over time through autonomous browsing, accumulation of a hierarchical knowledge store, periodic distillation, and generative output. The system is not a chatbot, a search assistant, or a recommendation engine. It is closer to a cultivated organism: given a habitat, movement rules, a memory architecture, and periodic free play, it is expected to develop into something more interesting than its starting point.

## What MVP Phosphene Actually Does

**The daily rhythm:** Every 4 hours, it pulls content from your subscribed sources (a Telegram channel, an RSS feed, whatever's configured). The Attention Filter scores each piece against your seed personality criteria — "does this matter to the kind of mind that wrote this corpus?" — and the survivors get stored as Tier 1 notes with cross-references and importance scores. Once a day, it generates a piece of writing from accumulated personality context and posts it to Telegram. Once a day, it runs decay on notes that aren't earning links.

**The developmental arc:** As Tier 1 notes pile up, distillation gates eventually pass. RAPTOR clusters the notes into Tier 2 patterns — "you keep encountering X from different angles." When enough patterns exist, T2→T3 reflect-evolve runs: the system looks at its patterns and proposes personality file updates. These personality files are what the Generator reads when it writes. So over weeks, the writing shifts because the personality substrate shifts.

**What you'd see on Telegram:** One post a day. Early on (bootstrap), nothing — the system is ingesting and clustering silently. After the first T2→T3 cycle produces personality files, posts start appearing. They'd be prompted generation: an essay, observation, question, or provocation derived from the current personality context plus whatever unresolved Tier 2 threads exist. If you message it, it responds in character.

### Feeding It

There are two Telegram-based input paths:

- **Channel adapter** — subscribes to a Telegram channel (yours or someone else's). Good for content streams: news, curated topic channels, other people's writing.
- **Human-share adapter** — you DM the bot directly. Plain text becomes source content (your musings, half-formed thoughts). URLs get fetched and ingested with your accompanying text preserved as annotation. This is the primary ongoing feed mechanism after corpus seeding.

### What's Missing vs. the Full Vision

**No spontaneity.** MVP runs on a clock. The full Orchestrator would notice high unresolved tension in the memory graph and trigger extra activations, or let the system deviate mid-task when something structurally interesting pulls harder than the scheduled work.

**No lateral movement.** When the system generates, it generates the prompted output and stops. The full version would finish the prompted task and then, if remaining budget exists and tension is high, take a free-play turn — writing something self-initiated about whatever threads have high unresolvedness × link density.

**No ambient awareness.** The Generator doesn't know what time of day it is, how much budget it's used, how long since you last interacted, or what the memory graph looks like from the outside. The full version would feed all of this in, and the system could do whatever it wants with it.

**No feedback loop.** When you react to a post or reply, nothing happens. The full system would use your reactions to bump unresolvedness on the source notes that led to that output — "this thread is alive, keep pulling on it."

**No exploration.** The system only sees what its configured sources give it. The full Explorer would follow links in accepted content, evaluate new sources, and propose subscriptions.

## The Full MVP Cycle, Step by Step

### Ingestion Activation (every 4 hours)

| Step | What happens | Type |
|------|-------------|------|
| Source poll | Telegram API / RSS fetch / read local files | **Deterministic** (network I/O) |
| Content normalization | Truncation, URL extraction, timestamp parsing | **Deterministic** |
| Embed items for retrieval | Each content item → vector via toolkit/embedding | **Embedding model call** |
| Similar note lookup | Memory Store vector search for nearby existing notes | **Deterministic** (cosine math on stored vectors) |
| Density metrics read | Note count, link degree, unresolved count from index | **Deterministic** |
| Blend weight computation | How much to weight prompt criteria vs. structural signals | **Deterministic** (formula on density metrics) |
| Score prompt criteria | "Does this content match personality criteria X, Y, Z?" | **LLM call** — per item |
| Extract incoming assertions | "What claims does this content make?" | **LLM call** — per item, only when Phase 2 is active (network density > threshold) |
| Structural scoring | Link density, unresolvedness affinity, friction, cluster novelty | **Deterministic** (graph math on Memory Store) |
| Composite score + threshold | Blend prompt × weight + structure × weight, compare to threshold | **Deterministic** |
| Wild-card sampling | Random sample from below-threshold items | **Deterministic** |
| Annotation generation | "Why was this content retained?" | **LLM call** — per accepted item |
| Store accepted notes | Write Tier 1 markdown with frontmatter, update index | **Deterministic** (file I/O) |

A single ingestion cycle with 10 content items where 3 are accepted and Phase 2 is active: **10 prompt-scoring LLM calls + 10 assertion-extraction LLM calls + 3 annotation LLM calls + 10 embedding calls = 33 model calls.** Early on (Phase 2 inactive, low density), assertion extraction is skipped: **10 + 3 + 10 = 23 calls.**

### Distillation Activation

#### T1→T2 (every few days, when gates pass)

| Step | What happens | Type |
|------|-------------|------|
| Gate check | Query Tier 1 count since last run, read metadata timestamps | **Deterministic** |
| Embed notes | All pending Tier 1 note texts → vectors | **Embedding model call** |
| RAPTOR clustering | Cluster vectors, then summarize each cluster | **LLM call** — one per cluster (summarization) + re-embed summaries |
| Coherence gating | Mean pairwise cosine similarity per cluster | **Deterministic** (math) |
| Write Tier 2 notes | Store cluster summaries as Tier 2, add links | **Deterministic** (file I/O) |
| Assertion cache | Extract assertions from each cluster summary | **LLM call** — one per coherent cluster |

#### T2→T3 (~monthly)

| Step | What happens | Type |
|------|-------------|------|
| Reflection | "Look at these patterns — what recurring tensions, contradictions, evolutions do you see?" | **LLM call** — one call with all Tier 2 patterns |
| Evolution | "Given these insights and current personality files, propose updates" | **LLM call** — one call with personality context + reflection output |
| Inertia calculation | Version-count-based resistance to change | **Deterministic** (formula) |
| Compression check | Proposed personality files can't lose too much content | **Deterministic** (length comparison) |
| Personality writeback | Supersede old personality files, bump version counts | **Deterministic** (file I/O) |
| Criteria adjustments | Feedback-derived weight changes for attention criteria | **Deterministic** (engagement rate math) |

### Generation Activation (daily)

| Step | What happens | Type |
|------|-------------|------|
| Load personality context | Read Tier 3 files from vault | **Deterministic** (file read) |
| Load Tier 2 enrichment | Search for relevant patterns via embedding | **Embedding model call** |
| Skeptical memory check | Verify Tier 3 claims against recent Tier 1 | **Deterministic** (note queries) |
| Generate output | Full prompted generation from personality + patterns + prompt | **LLM call** — the actual writing |
| Route to platform | Decide format (text/markdown/telegraph) by length | **Deterministic** |
| Deliver via Gateway | Send to Telegram | **Deterministic** (API call) |

### Decay Activation (daily)

| Step | What happens | Type |
|------|-------------|------|
| Scan notes | Query all notes, compute link-density decay | **Deterministic** |
| Apply decay | Reduce importance of low-link notes | **Deterministic** |
| Prune | Mark fully decayed notes as superseded | **Deterministic** |

**Zero model calls.** Pure graph maintenance.

### Cost Summary

| Activation | Frequency | LLM calls | Embedding calls |
|-----------|-----------|-----------|-----------------|
| Ingestion | Every 4h | N (scoring) + N (assertions if Phase 2) + A (annotations) | N (retrieval) |
| Distillation T1→T2 | Every few days | C (summaries) + C (assertion cache) | N (notes) + C (re-embed) |
| Distillation T2→T3 | ~Monthly | 2 (reflection + evolution) | 0 |
| Generation | Daily | 1 | 1 |
| Decay | Daily | 0 | 0 |

Where N = content items polled, A = items accepted, C = coherent clusters formed.

The attention filter is by far the most API-intensive module on a per-activation basis. Most of the system's daily token budget goes to deciding what to pay attention to, not to the writing itself.

## Project Status

7 modules complete, 574 tests passing, 98% coverage.

### What's Built

**Memory Store** — Three-tier hierarchical memory (daily log → pattern layer → personality files). CRUD, index layer, embedding search, graph operations, decay with link-density weighting, supersession, density metrics API.

**Attention Filter** — Personality-driven content selection. Prompt-criteria scoring (LLM), structural scoring (link density, unresolvedness, friction, cluster novelty), triple-gate blend that shifts from prompt-weighted to structure-weighted as network density grows, assertion extraction, annotation generation, wild-card sampling, near-miss recording.

**Source Ingestion** — Adapter framework with RSS, Telegram channel, Reddit, human-share (DM the bot), and corpus import (LiveJournal, Twitter, blog, plain text). Durable last-seen markers. URL fetching for shared links.

**Gateway** — Multi-platform message bus. Telegram outbound (text/markdown/telegraph), inbound polling, feedback signal dispatch (reactions/replies/forwards/edits). Adapter registry with local log fallback.

**Generator + Output Router** — Prompted, response, and free-play generation from personality context. Skeptical memory verification (checks Tier 3 claims against recent Tier 1). Output routing by intent tag and content length. Provider-failure rotation.

**Distillation** — T1→T2: RAPTOR clustering with coherence gating, assertion cache. T2→T3: two-step reflect-evolve with version-count inertia, personality supersession, compression caps, feedback-derived criteria adjustments. Gate evaluation, consolidation locking, persisted run metadata.

**Feedback Collector (Phase 7.1)** — In-memory output tracking, immediate feedback normalization (reactions/replies/forwards → feedback events), Tier 1 feedback-note writes, silence detection, bounded pruning, positive-feedback unresolvedness bumps.

### Pre-Module-7 Hardening

Two hardening phases implemented recommendations from an external design review:

- **Attention Filter additions** — Wild-card accepts (random below-threshold sampling to prevent filter tunnel vision) and near-miss recording (items that almost passed, annotated for later review).
- **Unresolvedness + Diagnostics** — Pure `compute_unresolvedness()` utility decoupled from Memory Store, and `tools/network_diagnostics.py` for inspecting memory graph health (link density distribution, unresolved thread counts, cluster statistics).

### What's Left to MVP

**MVP Orchestrator** — 3 phases wiring all existing modules into a running system:

1. Public types, config validation, croniter-based cron loop, start/stop/trigger lifecycle
2. Activation wiring: ingestion (poll→filter→store), distillation (gates→distill), generation (bootstrap check→generate→route→send), respond (Gateway listener), decay
3. Error isolation, activation logging, bootstrap transition proof, end-to-end integration test, restart recovery

After that: seed corpus, configure adapters, deploy as systemd service.
