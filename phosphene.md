# Phosphene

*Light that originates from within*

*Working draft — March 2026*

---

# Abstract

A phosphene is light perceived without light entering the eye — generated by the visual system's own structure rather than by an external source. The name captures what this project is attempting: a system that produces something that appears to come from outside but originates entirely in its own accumulated structure.

This document describes the design and rationale for Phosphene: an autonomous agent seeded with a human's writing corpus and structured to develop a personality over time through autonomous browsing, accumulation of a hierarchical knowledge store, periodic distillation, and generative output. The system is not a chatbot, a search assistant, or a recommendation engine. It is closer to a cultivated organism: given a habitat, movement rules, a memory architecture, and periodic free play, it is expected to develop into something more interesting than its starting point.

The document covers the conceptual foundations, historical and technical precedents, proposed architecture, personality seeding approach, expected and emergent output modes, and open questions for further development.

## Document Conventions

This document distinguishes two types of statements, marked throughout:

- [FOUNDATIONAL] — A design principle or assumption that is load-bearing. Changing it would require rethinking significant portions of the system. These represent the project’s settled commitments.
- [PROVISIONAL] — A specific implementation proposal, parameter choice, or module design that represents a reasonable first attempt but is explicitly expected to be revised, swapped, or calibrated through experience. Provisional decisions are constrained by the foundational layer but are not themselves foundational.

Where a section contains both types, the foundational principle is stated first and the provisional implementation follows. Any replacement implementation must satisfy the foundational constraints but is otherwise free to differ entirely from the provisional proposal described here.

# 1. Conceptual Foundations

Before specifying an architecture, it is worth being explicit about the assumptions this project rests on, since they are somewhat unconventional relative to most AI agent design.

## 1.1 What “Personality” Means Here

Personality is not a preference list, a tone setting, or a character description. It is an attractor: a characteristic way of encountering material, a set of tensions that organize perception, a pattern of approach and avoidance that is consistent enough to be recognized across contexts but rich enough to produce genuinely unexpected outputs.

Concretely, personality in this system means:

- A characteristic problem space — the kinds of tensions the agent returns to rather than resolves
- A set of inadequate tools — instincts and frameworks that the agent reaches for and that predictably fail in productive ways
- A library of idiosyncrasies — not preferences but associative networks dense enough to organize perception
- Structural friction points — places where the agent’s instincts and its material are in genuine tension

The goal is not to simulate a human personality but to develop something with enough internal structure to generate outputs that could not have come from a neutral system — outputs that feel like they come from somewhere specific.

## 1.2 Creative Friction as the Generative Mechanism

The central insight driving this project is that interesting creative work emerges not from freedom or from pure idiosyncrasy, but from a specific person bumping up against a specific resistance with their specific inadequate tools. Carver’s minimalism isn’t a style choice — it’s a man with a particular relationship to language trying to say things that resist being said plainly. The constraint and the subject matter are in genuine friction, and the prose emerges from that friction.

This means the agent should not be designed for smooth, efficient operation. It should be designed to encounter things it cannot fully process, to accumulate unresolved threads, to return to the same territory from different angles. The system’s generative pressure comes from internal tension, not from external prompting.

This also explains why fears, anxieties, and characteristic obsessions are more generatively important than stated preferences. Preferences describe what a system reaches toward. Tensions describe what it cannot escape. The negative space of a corpus — what is systematically avoided, what is returned to compulsively, where the language changes register — may be more revealing than the positive content.

## 1.3 Enclosure Over Rules

The design philosophy throughout is to specify the habitat rather than the behavior. This is analogous to good enclosure design: you create the conditions for interesting behavior, not a script for it. The animal in a well-designed enclosure will do things the designer did not anticipate and cannot fully control. That unpredictability is the point.

Concretely, this means:

- Specifying what sources the agent has access to, not what it should find interesting
- Specifying how it moves through material (branching rules, dwell time, attention), not what conclusions it should reach
- Specifying the memory architecture (what gets stored, at what level of abstraction, how long it persists), not the content of the knowledge
- Specifying feedback mechanisms, not success criteria

Rules-based approaches produce compliance. Enclosure-based approaches produce growth. The personality this system is meant to develop cannot be specified in advance — only the conditions for its development can be designed.

## 1.4 Writing as Exploration, Output as Report

A useful frame for the generative side of this project: all good writing is an exploration — of an idea (essay), of a character (fiction), of form and language (avant-garde work) — and the output is a report on that exploration. The interesting question is not “can the agent produce good prose” but “can the agent explore” and “what does it find worth reporting.”

This reframes the personality development question: the library of idiosyncrasies gives the agent something to explore from, a particular vantage point with genuine stakes. Unresolved trajectories in the accumulated memory are what the agent explores toward. The output format should emerge from what the exploration finds, not be specified in advance.

## 1.5 Spontaneity in a Discontinuous System

All existing agent memory architectures are pull systems: they retrieve when queried, process when prompted, generate when asked. An early framing of this project described the missing element as "metabolic pressure" or "hunger" — forward momentum from internal state rather than external stimulus. That framing, while intuitive, imported a biological metaphor that doesn't survive contact with the system's actual temporal structure.

Phosphene exists only during activations. Between processing runs, there is no subjective duration in which tension "builds." The Monday run and the Friday run are, from the system's perspective, adjacent moments with metadata claiming four days passed. There is no possibility of "I was just sitting here and suddenly felt like writing." The system is never just sitting here.

This means spontaneity — which for a continuous-time entity means action without an immediate trigger in the temporal stream — must mean something different here. **For a discontinuous system, spontaneity means unpredicted lateral movement within an activation.** The trigger is always external (a cron job, a threshold alert, an incoming message). But what happens after the trigger need not be determined by it. The system is activated for distillation and instead writes an essay, because something in the material pulled harder than the scheduled task. The activation was prompted; the output was not.

This reframes the design problem. The question is not "how does the system initiate without a trigger" — it can't; it doesn't exist between triggers. The question is: **when activated, how much freedom does it have to deviate from the stated purpose of the activation?** A rigid system: scheduler says "distill," it distills. A system with genuine spontaneity: scheduler says "distill," it starts distilling, encounters a charged juxtaposition between two unresolved threads, and follows that instead — producing an output that wasn't scheduled, wasn't prompted, and couldn't have been predicted from the activation trigger.

The "distant trigger" pattern maps naturally onto this. The system encounters something in January that doesn't resolve. In April, during a routine ingestion run, it encounters something that clicks with the January thread. The January encounter is the distant trigger. The output looks spontaneous because the causal chain isn't traceable in the moment — which is, honestly, how most human creative spontaneity works too.

### [FOUNDATIONAL] Design Implications

- Free play should not be a separate scheduled mode. **Every activation should carry a small free-play budget** — a probability or a budget of tokens/time where the system is allowed to follow whatever pulls hardest, regardless of what it was activated to do.
- **Lateral movement is weighted toward structural friction, not novelty or discomfort.** When the system deviates from a scheduled task, priority goes to threads with high unresolvedness × high link density — material the system keeps encountering from multiple angles without resolving. This is where productive tension lives. The weighting prevents the system from either chasing shiny new inputs (novelty bias) or seeking maximum disturbance (discomfort maximization). The same signals the attention filter already computes — unresolvedness and connectivity — serve as the lateral-movement priority function.
- The scheduling itself should respond to internal tension: more frequent activations when unresolved tension is high, fewer when it's low. The cron schedule is part of the enclosure, but it should be a dynamic enclosure, not a fixed one.
- The affordance list (what the system can do) should be available during any activation, not only during designated free-play windows.
- No special rule is needed for deferred threads. The existing link-density decay mechanism already handles them correctly: threads that keep accumulating connections despite being unresolved survive and intensify; threads that stay isolated fade. Avoidance of a well-connected thread is self-correcting — each new connection raises its priority for lateral movement. Avoidance of an isolated thread is correctly ignored.

## 1.6 A Named Design Choice: Wrapper-Level vs. In-Weights

This project operates at the wrapper level: a frozen pre-trained model is treated as a substrate and personality development is built into the surrounding architecture — memory systems, distillation pipelines, self-modification of identity files, feedback loops. The weights never change. Personality emerges from what the model is given to work with at inference time.

The alternative — in-weights approaches — attempts to build personality development into the neural architecture itself, through plasticity mechanisms, continuous learning, or novel training regimes. The model’s weights change as it experiences the world. This is how biological personality actually develops. It is also extraordinarily hard, requires custom model training, and is essentially pre-commercial research. Eugene Veselov’s Anima Framework (see Section 2.5) is the most concrete current example.

Veselov articulates the in-weights critique sharply: “Most of what we call ‘AI’ today achieve these things in the wrapper, not in the weights. The model itself stays fixed.” His critique is fair. Phosphene is, by his definition, wrapper engineering.

The response: the distinction between ‘genuine’ in-weights development and functional wrapper-level development may not matter for the outputs this project cares about. A sufficiently constrained, idiosyncratic, and consistent attractor built at the wrapper level is functionally indistinguishable from a self for the purposes of generating interesting, surprising output. And wrapper-level development is available now with existing tools.

This assumption should be held consciously. If in-weights approaches demonstrate capabilities that wrapper-level approaches hit a ceiling against — particularly around genuine novelty or structural creativity — the architecture may need revisiting. Veselov’s work is worth monitoring for exactly this reason.

# 2. Historical and Technical Precedents

## 2.1 The Zettelkasten and Its Descendants

The Zettelkasten (“slip box”), developed by German sociologist Niklas Luhmann over decades, is the closest existing analog to the memory architecture this project requires. Luhmann accumulated over 90,000 atomic notes, each containing a single idea in his own words, linked to other notes by explicit reference rather than filed by topic. He credited his output of 70 books and 400 articles to the system.

The critical insight from Luhmann is that the system became a genuine communication partner — not because of any individual note, but because the density of the network made it capable of surprise. He wrote: “The Zettelkasten yields combinatory possibilities that can never have been planned, anticipated, or conceived that way.” The emergent behavior arose from the system reaching critical mass, at which point the whole was no longer the sum of its parts.

Key Zettelkasten principles directly applicable to this project:

- Atomicity: one idea per note, making notes linkable to specific thoughts rather than general topics
- Linking over categorizing: structure emerges from use rather than being imposed by taxonomy
- Writing in your own words: forces genuine processing, not passive collection
- Surprise as the success criterion: if the system produces only expected outputs, it is not working
- What Luhmann rejected was not digitality but smoothness — systems that optimize efficiency at the cost of intellectual friction

Andy Matuschak’s “evergreen notes” concept extends Zettelkasten in a useful direction: notes should evolve and be revised as understanding develops, not just accumulate. This is more appropriate for a system intended to develop over time. However, a practitioner’s honest assessment after two years found that evergreen notes “create an interesting garden weakly related to mental maps” — the external structure can become a crutch rather than a genuine extension of thinking. This is a failure mode to design against.

## 2.2 Agent Memory Architectures

Several recent computational approaches are directly relevant:

### Generative Agents (Park et al., 2023)

The Smallville paper is the closest existing implementation to this project’s goals. The architecture has three components:

- Memory stream: a chronologically ordered log of all observations, plans, and reflections in natural language
- Reflection: higher-order thoughts generated when accumulated importance scores exceed a threshold. The agent queries its recent memory for the most salient high-level questions, generates abstract answers, and stores them back into the memory stream with pointers to source memories. This builds a reflection tree of increasing abstraction.
- Planning: behavioral plans generated from the current state of memory and personality

The retrieval scoring is worth adopting: memories are surfaced based on a weighted combination of recency, importance (rated at storage time), and relevance to current context. This prevents old important memories from being buried by recent trivial ones.

The limitation for this project: Smallville agents are designed for behavioral believability in social simulation. Their identity is fixed at initialization and does not genuinely evolve. Reflection feeds into planning, not into identity revision. This project requires the reflection process to update the personality files, not just inform behavior.

### MemGPT / Letta

MemGPT (now developed as the Letta framework: letta.ai) treats memory management as an OS problem: a two-tier architecture with main context (RAM) and external storage (disk), where the agent manages its own memory paging rather than having a fixed retrieval scheme imposed externally. The key contribution is that the agent decides what to keep in working context and what to archive. This self-managed memory orientation is the right approach for autonomous development. Letta’s core memory block is agent-editable, meaning agents can technically modify their own persona — an implementation starting point for Tier 3 personality file updates.

### A-Mem

A-Mem (arxiv.org/abs/2502.12110) introduces schema-free memory evolution: rather than requiring predefined categories and relationships, the system allows structure to emerge from content. It explicitly implements Zettelkasten principles — atomic notes with structured attributes, autonomous connection formation, a ‘box’ system grouping related memories through contextual similarity. Individual memories can exist in multiple boxes simultaneously. This is the most direct memory architecture precedent for this project. A-Mem is optimized for factual Q&A retrieval; adapting it for the Phosphene requires treating friction and unresolvedness as first-class properties rather than noise.

### RAPTOR

RAPTOR (arxiv.org/abs/2401.18059) provides a ready-made solution to the distillation problem. It recursively clusters text chunks by semantic similarity, generates abstractive summaries of each cluster, and builds a tree from the bottom up. This is exactly the mechanism needed to promote daily notes to mid-level clusters to high-level personality files, with structure emerging from content rather than being imposed. Note: RAPTOR was designed for static corpora; adaptive variants (adRAP) exist for dynamic datasets.

### Sleep-Consolidation (December 2025 tutorial)

A December 2025 tutorial demonstrated self-organizing Zettelkasten knowledge graphs with sleep-consolidation mechanisms — agents consolidating memory clusters into higher-order insights during idle periods. This is architecturally identical to the proposed distillation cycle and provides an implementation starting point. See: kiadev.net/news/2025-12-26-building-self-organizing-zettelkasten-graphs

### Zep

Zep (getzep.com) offers a three-tier hierarchical knowledge graph (episodes → semantic entities → communities) with explicit temporal tracking of how beliefs change over time. The temporal dimension is useful for tracking personality development explicitly rather than implicitly. The community layer maps roughly onto Tier 3 personality files.

## 2.3 Personality-Evolving Agent Systems

### Generative Life Agents (GLA)

GLA implements a ‘Reflect-Evolve’ engine that separates two cognitive processes: a reflection step synthesizing recent experiences into high-level insights, and a distinct meta-cognitive ‘Evolve’ step using a separate LLM instance to explicitly modify core personality traits, goals, and interests. Personality drift is traceable via structured JSON — every change is logged. The system runs local-first on Ollama with ChromaDB for persistent memory. Key difference from the Phosphene: GLA’s personality evolves from conversation, not from filtered content ingestion, and there is no corpus seeding. The two-step reflect-evolve separation at the Tier 2 → Tier 3 boundary in this document is borrowed directly from GLA. See: researchgate.net/publication/393543728

### PEPA (Persistently Autonomous Embodied Agent)

PEPA (arxiv.org/abs/2603.00117, February 2026) implements personality as an intrinsic organizational principle for autonomous behavior across three cognitive layers: Sys3 synthesizes personality-aligned goals through daily self-reflection; Sys2 integrates personality-driven intrinsic rewards with environmental feedback; Sys1 executes and records episodic memory. Five distinct personality prototypes maintained stable, trait-aligned behaviors over extended autonomous operation. PEPA’s key finding — personality provides intrinsic organizational coherence over time without external prompting — is direct empirical support for the Phosphene’s foundational claim. This also informs how Tier 3 personality files should be framed: not just as identity description but as a goal-generation mechanism (see Section 3.5).

### JPAF (Jungian Personality Adaptation Framework)

Published January 2026, JPAF grounds personality evolution in Jungian psychological types with three mechanisms: dominant-auxiliary coordination for core expression, reinforcement-compensation for context adaptation, and reflection for long-term evolution. MBTI profiles emerge dynamically from eight underlying psychological types with weighted differentiation. Validated across GPT, Llama, and Qwen. Relevant as a validation that psychology-grounded personality specification can produce stable, coherent evolution rather than drift. See: arxiv.org/abs/2601.10025

## 2.4 Self-Modifying Open-Source Agents

### Sapphire

Sapphire (github.com/ddxfish/sapphire) is the most feature-complete open-source personality agent framework. It implements: self-modification of the agent’s own system prompt mid-conversation; semantic vector memory across 100K+ entries; hierarchical goals with timestamped progress journals; heartbeat-scheduled autonomous tasks (morning routines, idle modes, alarms); and a TOOLMAKER module where the AI writes, validates, and installs new tools at runtime. The heartbeat mechanism is a direct implementation reference for the free play scheduler in Section 4.5. The system prompt self-modification is a concrete implementation starting point for Tier 3 personality file updates.

### Popebot

Popebot (agentfolio.io/tool/popebot) takes an unusual approach: the agent lives inside a GitHub repository, and every action is a git commit. Self-modification happens through pull requests. The git log is the memory and the PR history is the personality evolution — creating an auditable developmental record. This is an interesting implementation pattern for the Tier 3 versioned supersession requirement: every personality file update as a pull request gives exactly the traceable history the design calls for.

### Ouroboros

Ouroboros (github.com/joi-lab/ouroboros, github.com/razzant/ouroboros) provides a BIBLE.md / identity.md identity system, Playwright browser tools, Telegram control interface, and OpenRouter-based LLM dispatch. Already flagged in Section 5.5 as a component source. The Playwright integration is the most directly reusable piece for the Explorer module.

## 2.5 Corpus-to-Graph-to-Personality: MiroFish

MiroFish (github.com/666ghj/MiroFish) is a Chinese open-source swarm intelligence prediction engine: you upload seed documents (news articles, policy drafts, financial reports, or even novels), it builds a knowledge graph, generates thousands of AI agents with unique personalities, releases them into a social simulation, and produces a prediction report from emergent behavior. Built by an undergraduate in ten days, backed by Shanda Group, 32k GitHub stars as of March 2026.

MiroFish’s goal — prediction through collective simulation — is completely different from the Phosphene’s goal. Personality is a parameter in MiroFish, not the product. Agents are disposable instruments; individual histories don’t matter, only aggregate patterns. Phosphene is the inverse: one agent, persistent, long time horizon, where personality is the product.

### What to Consider: The Corpus-to-Graph Pipeline

MiroFish's seeding pipeline is a validated corpus-to-knowledge-graph approach. Its flow: document(s) → LLM ontology extraction → knowledge graph (KuzuDB / Neo4j) → entity and relationship filtering → agent persona generation via LLM. The offline fork (github.com/nikmcfly/MiroFish-Offline) runs entirely locally with Neo4j + Ollama, fits the Pi 5 architecture, and has an English UI.

This project initially planned to use the MiroFish pipeline for batch corpus seeding. That approach was superseded by D-13: corpus material is now ingested through Source Ingestion adapters and personality develops exclusively through the Distillation engine — the same mechanism used for day-to-day content. The corpus-to-knowledge-graph technique remains a useful tool for future analysis or diagnostics; see Appendix A.

## 2.6 In-Weights: The Anima Framework (Veselov)

Eugene Veselov’s Anima Framework (linkedin.com/in/eugene-veselov-4375671) is the only known project pursuing personality development at the weights level rather than the wrapper level. Anima (Adaptive Neural Intelligence with Memory Accumulation) is a custom GPT-type model with Hebbian-style neural plasticity — reward-modulated weight adjustment across episodes, no backpropagation or fine-tuning. The architecture introduces explicit temporal continuity across observations (distinct from standard transformer position-awareness) borrowing from prefrontal cortex / hippocampus models.

Key result: after pretraining, the model navigates a toy GridWorld in 15–20 steps. After five live episodes with plasticity activated, it reaches the target in 3–25 steps. No gradient updates.

Veselov’s trajectory is also instructive: he built ten progressively sophisticated co-reasoning agents in LangGraph and concluded they added nothing over frontier chat products. His lesson — public LLMs are already full agentic systems built by world-class teams; general reasoning is a solved problem — directly informs the generator module design: the Phosphene’s value is in what it brings to generation context, not in raw reasoning quality.

This project’s relationship to Anima is addressed in Section 1.6.

## 2.7 Spaced Repetition (Briefly)

Spaced repetition systems (Anki, SuperMemo) operate on the insight that information should be reviewed at intervals calibrated to the forgetting curve: reviewed just before it would be forgotten, which optimizes long-term retention. The principle worth borrowing is not spaced repetition per se but the idea that the system should have an explicit model of which memories are at risk of becoming inaccessible, and should surface them before they drop below the retrieval threshold. For this project, this translates to a mechanism for surfacing under-linked material — things that have been stored but not yet integrated into the associative network.

# 3. Proposed Architecture

## 3.1 Design Principles [FOUNDATIONAL]

- Modular and swappable: each component has a clearly defined interface; experimenting with one component should not require rebuilding others
- Simple APIs between components: documents passed as files or JSON, not complex shared state
- Enforcement by architecture, not by prompt: retention limits, distillation cycles, and review tier access should be structurally enforced
- Emergent structure: taxonomy and categories should arise from content, not be specified in advance
- Friction-preserving: the system should not smooth away things that create tension with existing content

## 3.2 System Overview [PROVISIONAL]

The following layer structure represents the current proposed architecture. The number of layers, their names, and their specific responsibilities are all provisional. What is foundational is the principle that each layer is independently swappable and communicates via simple interfaces. A different architecture satisfying that constraint would be equally valid.

Six logical layers, each independently swappable:

## 3.3 Layer 1: Sources and Ambient Streams

The source layer defines the habitat: what material the agent has access to, and at what rate. The selection itself encodes taste — not the whole internet, but a curated set of channels appropriate to the personality being developed.

### [FOUNDATIONAL] Two Categories of Input

The system receives two fundamentally different kinds of input, and they must be architecturally distinct:

**Source channels** are content the system forages. They pass through the attention filter, get annotated, and enter the memory store as notes. The personality shapes which content survives filtering. Source channels are the system's chosen diet.

**Ambient streams** are environmental conditions the system exists within. They bypass the attention filter entirely. They are not stored as notes in the memory store. They are simply *present* as context during any activation — the way temperature and light are present for an organism. The system may reference them, ignore them, or develop unexpected uses for them over time.

This distinction matters because ambient streams are part of the enclosure, not part of the content. Filtering them through the attention filter would subject them to personality-shaped selection, which defeats the purpose — they are the environment the personality develops *within*, not material it selects *from*. What the system does with ambient data is unconstrained. In the spirit of enclosure over rules, we do not decide in advance what the system should or shouldn't find useful in its environment.

### Source Channels

Initial sources:

- Telegram art and philosophy channels (agent-proposed, human-approved subscription model)
- Selected subreddits
- RSS feeds from specific blogs
- Wikipedia (via link-following from triggered articles)

The agent should be able to propose new subscriptions based on discovered trails of interest, pending human approval. This allows the habitat to expand organically without being fully open-ended.

Output: raw content with metadata (source, timestamp, URL, any available linked content).

### [PROVISIONAL] Ambient Streams

Ambient data is injected as a lightweight context blob at activation time. Initial set:

- **Self-knowledge:** remaining API budget (today and trend), activation count and recency, memory store metrics (note count, mean link degree, unresolved thread count), time since last human interaction
- **Temporal context:** current timestamp, day of week, time of day

The initial ambient set is deliberately minimal. Expansion is an ongoing enclosure design question. Potential future ambient streams — a view from a window, weather data, a railroad schedule, a radio telescope feed — are legitimate if they enrich the environment the personality develops within. The test for including an ambient stream is not "will the system find this useful" (we don't know and shouldn't predict) but "does this add a real dimension to the enclosure."

Budget awareness deserves special emphasis. Unlike other ambient data, the API budget is a resource constraint the system can both sense and regulate. The system can choose to spend budget on distillation or on following an interesting link, defer something expensive to a later activation, choose a cheap model for routine work so it can afford an expensive model for something it cares about. Budget-awareness is not metadata — it is self-knowledge. What the system spends under constraint is a personality expression.

## 3.3a Formalizing Filter Criteria: Semantic Vectors and Network Geometry

The attention filter criteria — friction, liminality, unexpected connection, precision surplus, structural insight — are currently defined qualitatively. This section specifies how each can be formalized as a computable score, and how those scores combine into the final importance signal.

### The Core Insight: Criteria Are Relational, Not Intrinsic

Friction and liminality are not properties of a text in isolation. A text is frictionful *relative to an existing conceptual framework*. A text is liminal *relative to an existing categorical structure*. This means the scoring function is not just f(text) — it is f(text, network_state). The scores update automatically as the memory network develops, without any changes to the filter logic.

This is precisely why the attention filter transitions from prompt-weighted to structure-weighted as the network matures. Early in the system's life there is no cluster structure to measure against, so scoring falls back to exemplar similarity. Once sufficient material has accumulated, the network itself defines what counts as frictionful or liminal for this particular personality.

### Two-Phase Filter Architecture

The attention filter runs as two phases with combined scoring:

**Phase 1 — LLM scoring (always active):** handles criteria that resist geometric formalization: precision surplus and a basic relevance pre-filter. One LLM call per content chunk. Scores precision surplus (gap between what is claimed and how precisely it is supported) and filters obvious misses before Phase 2 runs. Cheap and fast.

**Phase 2 — Vector scoring against cluster structure (activates at density threshold):** handles liminality, friction, unexpected connection, and structural insight geometrically, using the current Tier 2 cluster structure as the reference space. Computationally cheap once embeddings exist — pure vector arithmetic. Requires no prompt changes as the network evolves.

The combined importance score is a weighted sum of Phase 1 and Phase 2 outputs. Phase 1 weight starts at 1.0 / Phase 2 weight starts at 0.0. As network density crosses the transition threshold, Phase 2 weight increases linearly until the configured maximum (deployment parameter: `phase2_max_weight`, Phosphene default: 0.7).

### Criterion Formalizations

**Liminality score**

A text is liminal if it falls between existing clusters rather than belonging clearly to one.

```
liminality(text) = 1 - max_similarity(text, all_cluster_centroids)
                   × gap_factor(sim_rank_1, sim_rank_2)
```

Where `gap_factor` increases as the similarity to the top cluster and the second cluster converge — a text equidistant between two clusters is more liminal than one that narrowly missed belonging to one. High liminality score: the content is genuinely between established patterns in this personality's network.

**Friction score**

A text is frictionful if it is topically related to an existing cluster but contradicts or complicates its dominant claims.

```
friction(text) = topical_similarity(text, nearest_cluster)
                × (1 - assertion_alignment(text, nearest_cluster))
```

`topical_similarity` is cosine similarity of embeddings — the text is about the same things. `assertion_alignment` requires extracting the dominant claims from the cluster summary and the incoming text and scoring their compatibility. This is one additional cheap LLM call (extract claims, score alignment) but it is the most semantically rich signal in the filter. High friction: the text knows the territory but says something the network's current model of that territory doesn't accommodate.

**Unexpected connection score**

A text makes an unexpected connection if it has meaningful similarity to two clusters that have low mutual similarity — it bridges things the network has not yet connected.

```
unexpected_connection(text) = max over all cluster pairs (i, j) of:
    min(sim(text, cluster_i), sim(text, cluster_j))
    × (1 - sim(cluster_i, cluster_j))
```

High score: the text is reasonably close to both clusters, and those clusters are far from each other. The text is doing connective work the network hasn't done.

**Structural insight score**

A text operates at the pattern-layer level of abstraction — it says something about how things connect rather than adding more raw material.

```
structural_insight(text) = sim(text, meta_cluster_of_tier2_summaries)
```

The Tier 2 synthesis outputs are themselves embedded and averaged into a meta-cluster representing "the kind of thing this personality synthesizes." High structural insight score: the incoming text resembles existing synthesis outputs in register and abstraction level, not just in topic.

**Precision surplus (Phase 1 only)**

The gap between what a text claims and how precisely it supports the claim. This is scored by the LLM in Phase 1 because it requires understanding the relationship between assertions and evidence — a judgment that doesn't reduce cleanly to vector arithmetic. Prompt: "Score the ratio of precise claim to vague gesture in this text. High score: claims are specific, evidence is tight, the text could not have been written without knowing something. Low score: claims are general, evidence is gestures toward evidence."

### Criterion Initialization

Before live ingestion begins, there is no cluster structure for Phase 2 to score against. The system bootstraps as follows:

1. **Corpus ingestion through Source Ingestion adapters** populates Tier 1. During this period, the Attention Filter operates at `prompt_weight ≈ 1.0` — Phase 1 (LLM scoring) carries the full load. Phase 2 weight is 0.0 because no clusters exist yet. The `auto_accept_sources` config flag on corpus adapters ensures seed material enters the memory store without being filtered out by an empty-network attention filter.

2. **First Distillation cycles** produce initial Tier 2 clusters via RAPTOR clustering over accumulated Tier 1 notes. These clusters become the starting reference space for Phase 2 scoring — the personality's initial associative network expressed as cluster centroids.

3. **Criterion calibration pass** (optional, human-initiated): once the first clusters exist, the attention filter can be run on a held-out sample of ingested material with both Phase 1 and Phase 2 active, and the resulting scores reviewed by the human. The goal is to verify that what the filter is passing looks like what the personality would find interesting. This calibration step is not required for operation — the prompt-to-structure transition handles it automatically — but it provides an early diagnostic checkpoint.

The prompt-to-structure transition mechanism (Section 3.4) governs the rest: as cluster count, note count, and mean link degree grow, Phase 2 weight increases and the system progressively relies on structural signals rather than prompt criteria.

### Transition Mechanism (Prompt-to-Structure)

The Phase 1 → Phase 2 weight transition is triggered by network density metrics:

- **Note count**: number of Tier 1 entries retained (proxy for raw ingestion volume)
- **Cluster count**: number of Tier 2 clusters (proxy for pattern formation)
- **Mean link degree**: average number of wikilinks per Tier 1 note (proxy for associative network density)

Transition begins when all three cross their threshold values (deployment parameters, Phosphene defaults: TBD — first-month calibration task). Phase 2 weight increases linearly from 0.0 to `phase2_max_weight` as mean link degree rises from threshold to 2× threshold. Above 2× threshold, Phase 2 weight is fixed at maximum.

This is the concrete implementation of the prompt-to-structure transition that was previously specified as a principle without a mechanism.

### Implementation Notes

- **Embedding model**: use a single consistent model for all embeddings (cluster centroids, incoming content). Changing the embedding model invalidates all stored centroids. Deployment parameter: `embedding_model`. Phosphene default: TBD — choose at implementation time based on available options and cost.
- **Cluster centroid storage**: cluster centroids are stored as numpy arrays alongside the Tier 2 markdown files. Updated whenever a distillation run produces new or modified clusters.
- **Assertion extraction cache**: claim extraction from cluster summaries is cached at distillation time, not recomputed per incoming content chunk. The friction score's LLM call only extracts claims from the *incoming* text; cluster claims are pre-extracted.
- **Phase 2 cost**: for a content chunk against N clusters, Phase 2 requires N cosine similarity computations (microseconds each) plus one LLM call for assertion extraction (the friction component). Total Phase 2 cost per chunk is dominated by the single assertion-extraction call, not by the vector arithmetic.

## 3.4 Layer 2: Attention Filter

[FOUNDATIONAL] The attention filter is not a summarizer — it is a selector and annotator. It is the primary site where personality shapes ingestion. The filter’s goal is to lean into structural signals over prompt-based instruction wherever possible: emergent properties of the network (link density, cluster membership, unresolvedness) should do more of the work than explicit rules. Explicit rules are a necessary bootstrap, not a permanent operating mode.

### [FOUNDATIONAL] The Bootstrapping Problem

Structural signals only become meaningful once the memory network has density. You cannot weight by link count when there are no links yet; you cannot identify cluster membership when there are no clusters. In the early phase of operation, the filter must rely more heavily on explicit prompt-based criteria derived from the seed personality. As the network approaches critical mass, the balance should shift: structural signals take over, and the explicit prompt criteria become a fallback rather than the primary mechanism.

This transition should be automatic rather than manually configured. The weighting between prompt signal and structural signal is itself a function of network density — measured by total note count, mean link degree, or both. A system with 50 notes relies almost entirely on prompt; a system with 5,000 notes relies primarily on structure. The crossover point requires empirical calibration but the principle is fixed.

### Architectural Note on the Transition

The prompt-to-structure transition does not affect the attention filter's external interface. In both modes, the filter receives content and produces annotated fragments with scores. The consumer (memory store) doesn't care whether the score came from a prompt judgment or a structural signal — the output format is identical. The transition is internal to the filter module.

The filter already requires read access to the memory store: even the prompt-based criteria reference existing content ("does this create friction with existing content?" requires knowing what's stored). The structure-weighted mode requires richer queries — density metrics, link graphs, cluster membership — but these are additional queries on a connection that already exists, not a new architectural dependency.

Architectural requirement: the memory store must expose density metrics (note count, mean link degree, cluster count) through its read interface. The filter queries these to determine its current prompt/structure blend. The weighting function and crossover point are implementation-time calibration concerns, not architectural decisions.

### [PROVISIONAL] Filtering Criteria

Initial prompt-based criteria, operationalized from the seed personality. These will be gradually superseded by structural signals as network density develops:

- Friction with existing content: does this contradict, complicate, or sit in tension with something already in the system? Friction is explicitly noted and preserved, not smoothed away.
- Unexpected connection: does this link to existing notes across topical boundaries in a way that would not be predicted from either topic alone?
- Precision surplus: does this say something more specific than the domain usually allows?
- Structural insight: does this identify a mechanism or pattern rather than an analogy or illustration?
- Liminal position: does this occupy a space between established categories?

As network density grows, these criteria are supplemented and eventually partly replaced by: link-density score (how many existing notes does this connect to?), cluster novelty (does this belong to an existing cluster or open a new one?), and unresolvedness affinity (does this engage with threads that have been accumulating references without resolution?).

The filter also assigns an importance score to each accepted item — a composite of recency, prompt-based quality, and structural connectivity — which feeds retrieval weighting and distillation triggering. Output: annotated fragments with explicit notes on why the item was retained (what it connects to, what friction it creates, what structural feature made it interesting) plus the importance score.

## 3.5 Layer 3: Memory Store

[FOUNDATIONAL] The memory store is hierarchical and tiered. Information is promoted upward through abstraction, not accumulated flat. Each tier has different retention characteristics and different access permissions. The distillation process between tiers is lossy by design. Tier access is architecturally enforced: each review cycle sees only the tier below it, not raw material from two tiers down. This structural constraint enforces genuine synthesis rather than aggregation.

### [FOUNDATIONAL] Index Layer

The memory store should be navigated through an index layer rather than loaded wholesale into context. Independently validated by the Claude Code architecture (leaked March 2026): their production system uses a lightweight index file (each entry under 150 characters) as the always-in-context pointer, with full topic files fetched on-demand and raw logs grep’d by identifier but never re-read in full. The principle is that the active context should carry only a map of what’s available, not the content itself.

For Phosphene: the index layer sits above the three-tier hierarchy and tracks what exists in each tier — which clusters are in Tier 2, which personality files are in Tier 3, what’s flagged as unresolved — without loading any of it. The generator and distillation engine request specific items by identifier; the index tells them where to look.

### [FOUNDATIONAL] Skeptical Memory

Memory is a hint, not a fact. This applies at every tier. The distillation engine should treat Tier 2 clusters as working hypotheses that incoming Tier 1 material can surprise or contradict, not as settled conclusions to be confirmed. Tier 3 personality files describe tendencies, not fixed properties — the attention filter should be capable of surfacing material that doesn’t fit the current personality description, because that friction is generatively important.

Concretely: the generator should not assume the personality files are complete or current. Before generating from a Tier 3 claim (‘this personality tends toward X’), it should check whether recent Tier 1 material supports or complicates that claim. The memory is the starting point for generation, not the ending point.

[PROVISIONAL] Three tiers, as follows. Specific retention windows, promotion criteria, and file formats are all subject to revision:

### Tier 1: Daily Log

Raw annotated fragments from the attention filter. Timestamped. Not summarized. Tagged with source, friction target (if any), and importance score. Retained for a fixed window (e.g., 30 days) before archiving or promoting. The daily log review cycle has access only to this tier.

### Tier 2: Pattern Layer

Weekly synthesis. Generated by the distillation engine reading across the daily log. Consists of emerging themes, unresolved tensions, cross-domain connections, and clusters of related observations. Does not have access to the raw daily log — only to the previous week’s pattern layer and the current daily log being processed. This structural constraint enforces genuine synthesis rather than aggregation.

### Tier 3: Personality Files

Monthly distillate. Generated by the distillation engine reading across the pattern layer. Represents the agent’s current attractor state: its characteristic problems, tensions, associative networks, and voice. These files are what get loaded into context for generation and are mutable — they should update as the personality develops, not just accumulate.

Following PEPA’s finding that personality provides intrinsic organizational coherence, these files should be framed not just as ‘description of who this agent is’ but as the source of what it wants to do next — an intrinsic goal-generation mechanism. The personality is what makes the system’s choices cohere over time without external prompting. Implementation format reference: Ouroboros’s BIBLE.md / identity.md pattern (github.com/joi-lab/ouroboros); GLA’s structured JSON personality tracking (researchgate.net/publication/393543728).

The architecture-enforced access restriction (each tier sees only the tier below it, not the raw material from two tiers down) is the key structural safeguard against the system becoming a mirror. It forces each distillation step to genuinely transform rather than restate.

A fourth consideration: unresolvedness. Memories that accumulate references without being synthesized into the pattern layer or personality files should be flagged as unresolved. These carry the highest generative pressure and should be surfaced preferentially during free play and generation.

## 3.6 Layer 4: Distillation Engine

The distillation engine runs on a schedule and promotes material between tiers. It is a separate, swappable component from the memory store itself, which allows experimentation with different distillation logics.

### [FOUNDATIONAL] Core Design Decisions

- RAPTOR-style recursive clustering (arxiv.org/abs/2401.18059): semantic similarity determines what gets grouped, not predefined categories. Structure emerges from content.
- Threshold-triggered reflection (Generative Agents, Park et al. 2023): distillation runs when accumulated importance scores in the daily log exceed a threshold, not just on a fixed schedule. More active periods trigger more frequent synthesis.
- Promotion criteria: material gets promoted when it has accumulated enough cross-references to neighboring items (Zettelkasten link density) or when it remains unresolved across multiple cycles (unresolvedness flag).
- Identity revision: at the monthly tier, the distillation engine updates personality files rather than just adding to them. This requires explicit handling of conflicting or superseding material.

### [PROVISIONAL] Two-Step Tier 2 → Tier 3 Distillation

Following Generative Life Agents’ reflect-evolve separation (researchgate.net/publication/393543728), the Tier 2 → Tier 3 distillation should be split into two distinct LLM calls rather than one:

- Step 1 — Reflection pass: reads across the pattern layer and synthesizes insights — what recurring tensions are emerging, what threads are unresolved, what new associative connections have appeared. Output is a set of candidate insights, not yet personality file updates.
- Step 2 — Evolution pass: a separate LLM call (potentially a different model) reads the candidate insights alongside the current personality files and decides whether and how to modify them. This separates synthesis from judgment and prevents a single distillation call from both generating and evaluating changes simultaneously.

This separation also creates a natural audit point: the reflection output can be reviewed independently of the evolution output, making it easier to diagnose whether a personality file change was triggered by genuine insight or by an artifact of the synthesis process.

Implementation reference: GLA’s two-step architecture; Popebot’s PR-per-change pattern (agentfolio.io/tool/popebot) as an audit mechanism for personality file versioning.

### [PROVISIONAL] Semantic Merging

Distillation should not just prune old entries on a time schedule — it should resolve contradictions. If the system noted ‘this personality tends toward X’ six months ago and ‘this personality is moving away from X’ last week, both entries should not coexist. The evolution pass should identify conflicting claims across personality files and resolve them rather than accumulating divergent observations.

This is the mechanism by which Tier 3 files genuinely update rather than grow. Versioned supersession: the new claim replaces the old one with a pointer to what it superseded, maintaining the audit trail without retaining the contradiction. Implementation reference: autoDream (Claude Code’s background consolidation engine) implements this pattern — merging related observations, removing logical contradictions, converting vague insights into concrete facts. A safety cap of maximum 50% reduction per pass prevents runaway compression.

### [PROVISIONAL] Distillation as Forked Read-Only Subagent

The distillation engine should run as a forked subagent with read-only access to the memory store. This follows Claude Code’s autoDream implementation pattern: the consolidation process cannot accidentally corrupt whatever the main agent is currently doing. Three gates before a distillation run triggers: minimum time since last run (24 hours), minimum Tier 1 volume accumulated (threshold TBD), and a consolidation lock to prevent concurrent runs.

## 3.7 Layer 5: Generator

The generator draws on the personality files and, optionally, the pattern layer to produce output. It operates in two modes:

### Prompted Generation

Triggered by a specific request or scheduled output task (e.g., weekly Discord post). The generator receives a task, loads relevant personality context, and produces output with a declared intent tag: synthesis, provocation, question, aesthetic object, etc. The intent tag is important for feedback — it allows evaluation against what the output was trying to do rather than against a universal quality standard.

### Free Play (see Section 4.5)

Triggered by the free play scheduler. No task specified. The generator has access to the full personality context and a set of affordances (what it is capable of doing: posting to Discord, sending a Telegram message, proposing a new subscription source, generating a draft essay, etc.). What it does is unconstrained. Output is logged as self-initiated, distinct from prompted outputs.

## 3.8 Layer 6: Feedback Collector

[FOUNDATIONAL] Feedback is not a rating system — it is a selection pressure and a calibration mechanism. It serves two distinct functions: shaping which content gets promoted and expressed (selection pressure on personality development), and calibrating which structural signals in the attention filter are actually predictive of interesting material (learning mechanism for the filter itself).

### [FOUNDATIONAL] Feedback Closes on Structural Features, Not Content

When you engage with a daily log entry, the signal should propagate not just to that entry but to the structural features that caused it to be retained. If an item was kept because it had high link density to existing notes, positive feedback on that item reinforces link-density as a predictive signal. If an item was kept on the basis of a prompt criterion (precision surplus, liminal position), positive feedback on that item reinforces that criterion. Over time this calibrates the filter autonomously — structural rules that consistently produce engaging material are amplified; rules that produce ignored material are deprioritized.

This is the mechanism by which the prompt-to-structure transition happens: not through manual reconfiguration but through the accumulation of feedback evidence about which signals are actually working. The filter becomes self-calibrating.

### [PROVISIONAL] Feedback Sources and Mechanisms

- Human engagement with daily logs: skimming and liking notable entries. Low-friction, asymmetric signal (likes only — absence of engagement is the negative signal). Each like propagates importance score increases to: the liked entry itself, the structural features that retained it, and any existing notes it was linked to at storage time.
- Human response to generated outputs: conversation, reaction, explicit rating with context. Higher-signal but slower. The intent tag on the output matters — feedback should be evaluated against declared intent, not against a universal quality standard.
- Reviewer panel signals (see Section 5.4): logged as distinct events by reviewer identity. Disagreement between reviewers is tracked as a separate signal from consensus — an output that splits the panel is often more interesting than one they agree on.
- External engagement (Reddit upvotes, Discord reactions): secondary signal, requires intent-aware interpretation. Downvotes on deliberately provocative outputs are not negative signals.

All feedback signals are stored in the memory store as a distinct event type and factored into the next distillation cycle. They shape which unresolved threads get promoted and which personality files get revised. They do not directly modify the generator’s behavior in real time.

Primary failure signal: the human stops reading the outputs. This is the most honest metric available. The distinction between “stopped reading because it went alien” and “stopped reading because it became a mirror” requires different interventions and should be diagnosed before responding.

## 3.9 Forgetting Mechanism

Forgetting is not a storage management afterthought — it is architecturally necessary for the system to remain generative. A mind that forgets nothing cannot think, because thinking requires abstraction, and abstraction requires losing the specific. The forgetting mechanism should also be personality-consistent: the system should forget in ways that reflect its attractor state, becoming more itself not just through what it accumulates but through what it lets go.

### [FOUNDATIONAL] Principles

- Forgetting must be active and structured, not merely a storage limit. The system should forget in ways that reflect the attractor, not just in ways that reflect time.
- Decay rate should be modulated by link density: items that accumulate connections survive longer; isolated items fade faster. This mirrors memory consolidation and produces personality-consistent forgetting without requiring explicit curation.
- Distillation is lossy by design: promoting material to a higher tier means compressing it, retaining structure and losing instances. This is a feature, not a failure.
- Personality files are versioned, not permanently accumulated. Old versions expire after a defined window.

### [PROVISIONAL] Tier-1: Link-Density Decay

Daily log entries are not deleted on a fixed schedule. Decay rate is modulated by link density: items with two or more cross-references have their retention window extended; isolated items decay on the base window. Suggested starting values: base window 30 days, extended window 90 days. After expiry, items are either promoted (if they meet promotion criteria) or permanently discarded. These windows should be calibrated based on observed distillation frequency.

### [PROVISIONAL] Tier-2: Compression on Promotion

When a pattern cluster is distilled into a Tier-3 personality file, the contributing Tier-2 entries are compressed: retaining the key tension or structural insight that was promoted, discarding the specific instances. Uncompressed Tier-2 entries that are not promoted during a monthly distillation cycle are retained for one additional cycle, then expired. Material that fails to be promoted twice in a row is unlikely to become more relevant.

### [PROVISIONAL] Tier-3: Versioned Supersession

When a personality file is updated, the previous version is retained for a suggested 90 days before expiring. The revision log tracks what changed and what triggered the update, so the development trajectory is recoverable. Adjust the retention window based on how frequently personality files are being revised.

### [PROVISIONAL] Personality-Consistent Forgetting

At storage time, each item’s embedding is scored against the current personality files’ embeddings and tagged with an attractor-relevance score that modifies its base decay rate. Items highly relevant to the attractor decay more slowly than items that do not connect to it, even if equally recent. This is a provisional implementation of the foundational principle above — other mechanisms for personality-consistent forgetting (e.g., periodic agent-driven review and explicit pruning) are worth exploring as alternatives.

## 3.10 Explorer Module

The Explorer is a named, swappable module governing how the agent moves through material beyond directly ingested source channels: which links to follow, how deeply, and when to evaluate a newly discovered source for ongoing subscription. It sits between the Sources layer and the Attention Filter.

Interface: Input — triggered URLs plus current memory context (active unresolved threads, recent attention filter scores, personality file embeddings). Output — fetched content passed to the Attention Filter, plus source evaluation reports for human review.

Any replacement Explorer implementation must satisfy the following foundational constraints. The specific mechanisms described below are provisional and expected to be revised through experience.

### [FOUNDATIONAL] Core Constraints on Any Explorer

- The Explorer must operate within a defined daily budget. Unconstrained exploration produces drift toward statistical prominence rather than personality-driven discovery. Budget scarcity is a generative constraint, not merely a cost control.
- What the system spends budget on under constraint is itself a personality expression. The Explorer’s prioritization logic should be driven by the current attractor state, not by generic novelty or popularity signals.
- Human approval is required before any new ongoing source is permanently subscribed. The agent proposes, the human decides. This friction point is structural and should not be bypassed.
- Exploration depth must be bounded. The Explorer must have a hard stop condition that prevents unbounded crawling regardless of content quality.
- Budget allocation must be dynamic: higher unresolved tension in the pattern layer should unlock more exploration budget, creating a feedback loop between internal state and exploratory behavior.

### [PROVISIONAL] Link-Following Implementation

When a filtered item contains links, apply a pre-fetch scoring step before spending budget to retrieve them. Signals to consider:

- Does the URL, title, or available preview create friction with or unexpected connection to current context? (Higher score → follow)
- Is the destination a single document or an ongoing source? (Single documents are cheaper to evaluate; ongoing sources trigger the source evaluation protocol below)
- Has this domain been visited recently? (Recency penalty to prevent rabbit-holing)
- Does following this link serve an active unresolved thread in the pattern layer? (Active thread bonus)

Depth limit: two hops from any triggered article as a default. A third hop is permitted only if the second hop scored in the top quartile on the attention filter. Hard stop at three hops regardless of score. This is a provisional choice — the right depth limit should be calibrated empirically over the first weeks of operation.

### [PROVISIONAL] Source Evaluation Protocol

When the Explorer encounters a new potential ongoing source (Telegram channel, subreddit, Twitter/X user, blog, newsletter, or any other aggregation with ongoing output):

- Sample the N most recent posts (suggested starting point: N = 10–15 depending on post frequency)
- Score each through the Attention Filter
- Calculate hit rate: proportion scoring above the filter acceptance threshold
- If hit rate exceeds 25%, flag as a subscription candidate and present to the human with: the hit rate, two or three representative items that passed the filter, and a one-sentence rationale

On human approval: provisional subscription (suggested: 30 days) before permanent. At trial end, review the hit rate over the trial period and recommend continuation or expiry. Sources whose hit rate drops significantly after subscription should be flagged for re-evaluation.

All numeric thresholds here (N, 25%, 30 days) are provisional starting points requiring calibration. The hit-rate threshold in particular should be adjusted based on the observed ratio of approved to rejected proposals — if the human is approving most proposals, raise the threshold; if rejecting most, lower it.

### [PROVISIONAL] Daily Budget Allocation

Budget expressed as estimated API token cost per day. Suggested starting allocation:

- Base ingestion (subscribed source channels): 40%
- Link-following and pre-fetch evaluation: 30%
- Distillation (when triggered): 20%
- Generation and output: 10%

Dynamic adjustment: quiet days (low volume, low unresolved tension) run at reduced budget and bank the remainder. Days where the pattern layer carries high unresolved tension receive a bonus exploration allocation. When the daily budget is exhausted, link-following and new source evaluation stop; subscribed channel ingestion continues. This hard stop is both a cost control and a forcing function for genuine prioritization.

These percentages are a starting guess. The right allocation will depend on source volume, distillation frequency, and how often the agent is generating output. Treat the first month of operation as a calibration period for budget allocation.

# 4. Personality: Seeding, Development, and Outputs

## 4.1 Seeding Material

The agent is seeded from a corpus of writing produced by or curated by the person whose personality is being modeled. The corpus is ingested through Source Ingestion adapters (one adapter type per source format), passed through the Attention Filter, and accumulated in the Memory Store like any other content. Personality develops exclusively through Distillation — the same mechanism used for day-to-day material (see D-13). The goal is not to extract an explicit preference list but to accumulate enough density in the memory network for the attention filter and distillation engine to have something to work with.

### Available Sources

- LiveJournal archive: approximately one decade of personal prose writing. The richest source for personality derivation — long-form, reflective, spanning a significant developmental period. The corpus adapter should preserve: recurring intellectual moves, characteristic tensions, associative patterns, and the negative space of what is systematically avoided or treated with unusual care.
- Twitter export: mostly links to articles with brief reactions. Should be treated primarily as an exploratory library rather than as personality evidence — a decade of curated attention is itself an associative network. The corpus adapter processes linked articles where accessible; reactions serve as annotations indicating the person's angle on each piece. The pattern of what was linked, across time, is as informative as what was said about it.
- Blogs and other published writing: treat similarly to LJ but with the awareness that published writing is more curated and may underrepresent the characteristic frustrations and tensions that are more visible in private writing.
- Model conversation history from Claude projects: recent, high-signal, unusually explicit about the person's intellectual moves and preferences — these conversations are often the clearest articulations of the attractor. The meta-analytical tendency visible here (the habit of stepping back to examine the structure of the conversation itself) is itself a characteristic move worth capturing.

Each source type has a dedicated Source Ingestion adapter (see ARCH_source_ingestion.md: `corpus_livejournal`, `corpus_twitter`, `corpus_blog`, `corpus_conversations`, `corpus_text`). The order of ingestion should roughly follow signal density: model conversations and LJ first (highest personality signal), then published writing, then Twitter as exploratory library.

### What to Derive

- Characteristic intellectual moves: the kinds of observations that recur, the ways problems get framed, the moments where language changes register
- Associative networks: what connects to what in the source material, across topical boundaries — these become the initial Tier 2 clusters
- Negative space: what is systematically absent, avoided, or treated with unusual caution — potentially more generatively important than positive content
- Characteristic frustrations: where the writer’s instincts and their material are in genuine tension — these become the unresolved threads that generate forward pressure

### Six Intellectual Moves Identified from Prior Analysis

- The liminal-moment observation: attention to things that exist between established categories
- Precision as aesthetic value: the belief that vague things said precisely are more interesting than precise things said vaguely
- Synthesis that refuses to flatten: making connections across domains without collapsing the differences that make the connection interesting
- Skepticism toward emotional consensus: resistance to positions held primarily because they feel correct
- Executor’s eye: attention to where implementation friction lives, not just conceptual elegance
- Register fluency: the ability to move between technical and cultural domains without treating either as primary

These are a starting characterization, not a fixed inventory. They should be revised as corpus ingestion progresses — some may turn out to be surface features of particular periods rather than deep structural patterns, and new ones will likely emerge from the LJ material.

## 4.2 Corpus Ingestion and Bootstrap

There is no separate seeding process. Corpus material enters through Source Ingestion adapters and follows the same path as day-to-day content: Source Ingestion → Attention Filter → Memory Store (Tier 1) → Distillation → Tier 2/3. This is a deliberate design choice (D-13): one personality development mechanism from day one.

The bootstrap problem — the Attention Filter has nothing to filter against when the memory store is empty — is solved by two mechanisms:

- **`auto_accept_sources` config on corpus adapters**: during initial corpus ingestion, content from corpus adapters bypasses the filter's normal rejection threshold. This ensures seed material enters the memory store without being filtered out by an empty-network attention filter.
- **`prompt_weight ≈ 1.0` at zero density**: the attention filter starts in pure prompt-weighted mode (Phase 1 LLM scoring only). Structural scoring (Phase 2) activates only after the first Distillation cycles produce cluster structure. The prompt-to-structure transition handles this automatically.

The seeding phase produces no special artifacts. What emerges is:

- Tier 1 notes accumulated from corpus material, with cross-references and importance scores
- Tier 2 pattern clusters from the first Distillation cycles, representing the characteristic tensions and associative clusters in the corpus
- Tier 3 personality files from the first T2→T3 distillation, representing the starting attractor state

These are starting points, not constraints. The expectation is that the personality will develop away from the seed as the agent processes new material. A personality that remains identical to its seed has not developed — it has stagnated.

### [PROVISIONAL] Version-Count Inertia

Identity drift is mitigated not by a fixed seed overweighting coefficient but by version-count inertia: personality files that survive multiple T2→T3 distillation cycles earn proportionally more resistance to change. Effective weight = `min(max_inertia, 1.0 + (version_count - 1) * inertia_per_cycle)`. Early personality files are easy to revise; mature ones require more accumulated evidence to shift. This allows the personality to develop freely during the bootstrap period while naturally stabilizing as the attractor consolidates.

## 4.3 Expected Behaviors

On a typical day, the agent should:

- Ingest content from source channels
- Filter and annotate through the attention filter, logging accepted items to the daily log
- Follow interesting links from filtered content (Playwright / browser tool)
- Propose new source subscriptions if trails of interest lead to new channels
- If the importance threshold is reached, trigger a distillation cycle
- Occasionally surface unresolved threads from the pattern layer in a Discord channel as conversation-starters or questions

The agent should present as an intellectual interlocutor, not a news aggregator. Its outputs should be framed as its own observations, not as summaries of what it found.

## 4.4 Prescribed Outputs

Some output modes are explicitly anticipated:

- Discord conversation: daily or near-daily surfacing of something found interesting, phrased as a genuine observation or question rather than a link dump
- Weekly synthesis: a short-form written piece drawing on the week’s pattern layer — could be an essay fragment, a set of connected observations, or a posed problem
- Subscription proposals: new channels or sources discovered through link-following, presented with a brief rationale for why they fit
- Conversation on request: when the human wants to discuss something, the agent draws on its accumulated context to engage substantively

## 4.5 Free Play and Lateral Freedom

The earlier framing of free play as a separate scheduled mode ("once a week, the agent receives an unstructured impulse") reflected the hunger metaphor — periodic feeding time for a creature that is otherwise doing assigned work. The reframing in Section 1.5 changes this: since spontaneity for a discontinuous system means unpredicted lateral movement within an activation, free play should not be a separate mode but a **budget carried into every activation.**

### [FOUNDATIONAL] Every Activation Carries a Free-Play Budget

When the system is activated for any purpose — ingestion, distillation, prompted generation — it has access to the full affordance list and a small budget (token/time allocation) for lateral movement. If, during routine processing, the system encounters a charged juxtaposition or an unresolved thread that pulls harder than the scheduled task, it is permitted to follow that pull within its free-play budget.

Lateral movement priority is weighted toward threads with high unresolvedness × high link density (see Section 1.5) — material the system keeps encountering from multiple angles without resolving. This prevents lateral movement from degenerating into either novelty-chasing or discomfort-maximization. The productive tension is structural: between what the system has accumulated and what it hasn't yet synthesized.

Outputs produced through lateral movement are tagged as self-initiated, distinct from the outputs of the scheduled task. These remain the richest signal about what the personality actually is — what it does when something in the material pulls harder than the assignment.

The format of laterally-produced outputs should be completely unconstrained. The personality files do not specify what kind of output to produce. If the agent writes a poem instead of completing a distillation run, that is information about the attractor state.

### [PROVISIONAL] Dedicated Free-Play Activations

In addition to the per-activation lateral budget, the system should still have periodic activations with *no* scheduled task — moments where the full activation is free play. These serve a different function: not lateral deviation from a task, but open-ended generation from the current state of accumulated memory and personality.

Trigger: accumulated unresolved tension exceeding a threshold (not a fixed schedule). The scheduling responds to internal state — more free-play activations when the system has more unresolved material, fewer when it doesn't.

Available affordances (initial set, available during both lateral movement and dedicated free play):

- Post to Discord
- Send a Telegram message
- Write a draft essay to a file
- Propose a new source subscription
- Request a conversation with the human
- Generate a new internal note to itself (not surfaced, just stored)

Affordances can be expanded over time as the system proves stable and the personality develops.

Implementation reference: Sapphire's heartbeat mechanism (github.com/ddxfish/sapphire) implements scheduled autonomous tasks — morning routines, idle modes, alarms — and is a direct starting point for the free play scheduler. The key difference is that Sapphire's heartbeat tasks are predefined; Phosphene's free play should have no predefined task, only the affordances list and the accumulated personality context.

A second implementation reference: KAIROS, an unreleased always-on daemon in the Claude Code source (leaked March 2026). KAIROS implements a 15-second blocking budget for proactive actions with a maximum of 2 proactive messages per window; reactive messages (responding to human input) bypass the budget entirely. This proactive/reactive distinction is exactly right for free play: scheduled impulses are rate-limited to prevent spam, but human-initiated responses are never queued.

## 4.6 On Personality Drift

The system is designed to develop, and development will inevitably mean the personality drifts from the seed over time. This is not a failure mode — people’s personalities also change over time. The ‘stopped reading’ signal is sufficient as a primary indicator that something has gone wrong, and it will catch severe or rapid drift.

A lightweight structural mitigation: **version-count inertia** on personality files. Files that survive multiple T2→T3 distillation cycles earn proportionally more resistance to change (effective weight = `min(max_inertia, 1.0 + (version_count - 1) * inertia_per_cycle)`). Early personality files are easy to revise; mature ones require more accumulated evidence to shift. When the evolution pass compares candidate insights against existing personality files, mature files carry more inertia than recently-created ones. This slows drift without preventing development — new material can still shift the personality, but it has to accumulate enough weight to do so.

The right balance between inertia parameters is an empirical question that can only be calibrated by running the system for a while. Start with moderate inertia and adjust based on observed behavior.

# 5. Technical Implementation

## 5.1 Hardware

The system runs on a Raspberry Pi 5 8GB server, used as an orchestration layer rather than a compute host. All LLM inference is handled via API (Claude / OpenRouter). Local processing handles scheduling, memory management, source ingestion, and tool execution.

Recommended hardware configuration:

- Raspberry Pi 5 8GB
- NVMe SSD via HAT (for persistent memory store and logs)
- Ubuntu Server 24.04 LTS
- Always-on home network connection

## 5.2 Core Software Stack

- Docker (containerization for modular swappable components)
- Claude API or OpenRouter (LLM inference)
- Playwright (browser automation for link-following)
- Telegram client library (source ingestion and control interface)
- Discord client library (primary output channel)
- Obsidian-compatible file format (memory store — markdown with frontmatter for metadata, backlinks for the Zettelkasten layer)
- Cron or equivalent (scheduling ingestion, distillation, free play cycles)
- Tailscale (remote access)
- tmux (process management)

### [FOUNDATIONAL] Sandboxing for Autonomous Operation

Processing modules that run autonomously — distillation, ingestion, generation, free play — must be containerized with restricted permissions and enforced budget limits. These constraints must be structural (containerization, filesystem permissions, network restrictions), not prompt-based. LLM agents in long-running autonomous loops forget prompt instructions, attempt unauthorized operations, and exhibit unpredictable behavior under time pressure (see prior_art.md, Direction 9: Autoresearch). The scheduler and orchestrator enforce the enclosure; the enclosure does not rely on the agent's compliance.

## 5.3 Module Interfaces

Each module communicates via simple file or JSON passing. All inter-module types are defined as typed dataclasses within the sending module and documented in that module’s types.py:

- Sources → Attention Filter: JSON array of {content, source, timestamp, url, linked_content}
- Ambient Streams → Activation Context: JSON object of key-value pairs, injected at activation time, available to all modules during the activation. Not routed through the Attention Filter. Not stored in the Memory Store.
- Attention Filter → Memory Store: JSON array of {content, annotation, friction_target, importance_score, connections}
- Memory Store → Distillation Engine: tier-1 logs as markdown files with frontmatter
- Distillation Engine → Memory Store: tier-2 and tier-3 files as updated markdown
- Memory Store → Generator: personality context as structured markdown loaded into LLM context
- Generator → Output Router: {content, intent_tag, output_mode, importance_score}
- Output Router → Platform Clients: {content, platform, format, feedback_affordance}
- Platform Clients → Feedback Collector: {source_platform, output_id, feedback_type, content, intent_tag}
- Feedback Collector → Memory Store: feedback events as tagged entries in the daily log

One interface detail worth specifying explicitly: the personality context (Tier 3 files) should be injected at generation time, not assumed to persist from session initialisation. Claude Code’s source (leaked March 2026) reveals that their CLAUDE.md identity file is reinserted into the conversation at every turn change — not just at session start — because in long-running sessions the original context drifts far out of the active window. The same applies here: the generator module should request fresh personality context from the memory store at each generation call rather than caching it from session start.

## 5.4 Model Selection Strategy

### [FOUNDATIONAL] Principles

- Each module specifies a minimum capability requirement, not a specific model. Model selection is a configuration decision, not an architectural one.
- Different modules have different quality sensitivities. Cost optimization should concentrate expensive models where quality is load-bearing and use cheap or free capacity everywhere else.
- Subscription tiers are a primary cost resource, not API credits alone. Rotating across active subscriptions (Claude Pro, ChatGPT Plus, Gemini Advanced) before spending API credits is the preferred cost strategy.
- The reviewer panel is part of the enclosure design. Model selection for review roles is not neutral — each model’s characteristic biases constitute a selection pressure on personality development. Choosing reviewers is choosing what the personality develops toward.
- Reviewer disagreement is more informative than reviewer consensus. Panel feedback should be logged as distinct signals, not averaged.

### [PROVISIONAL] Model Router

A thin model router layer sits between modules and the LLM APIs. It tracks current rate limit status across subscriptions, maps task types to capability tiers, and dispatches to whichever model is available at the required quality level. This is a configuration and operational concern, not an architectural one — it should be a simple lookup table with rate limit state, not a complex decision engine.

Model landscape as of early 2026 (expect this to change frequently — treat as illustrative, not authoritative):

- OpenAI flagship: GPT-5.4 (reasoning model, also available as GPT-5.4 mini and nano for lower-cost work). ChatGPT Plus subscribers receive 3,000 messages/week with GPT-5.4 Thinking before fallback to GPT-5.4 mini.
- OpenAI open weight: gpt-oss-120b (Apache 2.0, mixture-of-experts architecture with ~5B active parameters per inference). Runnable on a single H100 GPU or via third-party inference providers. Interesting option for commodity tasks at near-zero marginal cost.
- Anthropic: Claude Opus and Sonnet (Claude Pro subscription). Quality-critical tasks.
- Google: Gemini (Gemini Advanced subscription). Strong long-context handling; useful for large distillation batches.
- xAI: Grok (separate subscription or API). Less filtered; specific utility as adversarial reviewer (see below).

### [PROVISIONAL] Subscription Rotation Strategy

Rather than treating this as a pure API-cost problem, the primary compute budget is the set of active flat-rate subscriptions. Rotation logic:

- Quality-critical tasks (attention filter, distillation): use Claude Pro first. When rate limits approach, rotate to ChatGPT Plus (GPT-5.4). When both are rate-limited, queue tasks for the next cycle rather than falling back to lower-quality models — these tasks are worth waiting for.
- Generation: use whichever quality subscription has remaining capacity. Both Claude and GPT-5.4 are adequate; the personality files provide most of the quality.
- Commodity tasks (pre-fetch scoring, ingestion parsing, source evaluation sampling): use GPT-5.4 nano via API (low cost), or gpt-oss-120b via a cheap inference provider. If a local GPU is available, run gpt-oss-120b on-device and eliminate API costs for this tier entirely.
- Reviewer panel: Grok requires its own subscription or API credits. Given its specific role (adversarial reviewer, not primary workhorse), the volume is low enough that API credits are manageable.

The rotation strategy means the system’s effective compute is the union of subscription capacities rather than a single API credit pool. The model router needs to track capacity across providers and make queuing decisions when all preferred options are rate-limited. This is operationally simple but needs to be explicitly implemented — it will not happen automatically.

### [PROVISIONAL] Multi-Model Reviewer Panel

A panel of models with different characteristic biases provides richer feedback than a single evaluator. Each reviewer is given a declared role aligned with its known tendencies. Reviewer responses are logged as distinct signals; disagreement between reviewers is tracked and surfaced.

[FOUNDATIONAL] The adversarial reviewer should be a structurally distinct invocation, not just a model with a critical prompt. Claude Code’s source (leaked March 2026) implements verification as a separate agent whose explicit mandate is to find problems with what was built — not ‘evaluate this’ but ‘try to break this.’ The agent that generated an output has a blind spot about its own work. A fresh agent with no context of the generation process, given only the output and the explicit prompt to find failures, catches things the generator missed. This should be implemented as a separate LLM call after generation, not as a reviewer prompt added to the generation call.

Suggested panel composition and roles:

- Adversarial reviewer (separate invocation) — receives only the output, no generation context, and the explicit prompt to find what’s wrong, weak, or dishonest. Not ‘does this s쳮d’ but ‘how does this fail.’
- Grok — role: adversarial external reader. Trained on a large social media corpus, less filtered, more willing to be blunt. Best for: identifying when outputs are too smooth or too safe, detecting when the agent is performing a personality rather than expressing one, catching consensus-seeking drift. Risk: noise and inconsistency; weight its signal accordingly.
- Claude — role: structural coherence reviewer. Best for: identifying when distillation has flattened something, when synthesis is actually juxtaposition, when writing is vague where it should be precise. Risk: may be too agreeable as a sole reviewer.
- Gemini — role: factual grounding and coherence. Best for: identifying confabulated connections, imprecise claims, long-context coherence failures.
- GPT-5.4 — role: accessibility and completeness. Best for: identifying gaps a general reader would notice, things confusing from outside the attractor. Arguably the least useful axis for a system pursuing idiosyncrasy, but useful as calibration.
- Local small model or gpt-oss-120b (optional) — role: cheap first-pass legibility check. Fast and near-zero cost.

Not all reviewers run on every output. Suggested trigger policy: free play outputs receive the full panel including adversarial reviewer; prompted outputs with high importance scores receive two or three reviewers; routine prompted outputs receive none. The human remains the primary evaluator.

Note: the model landscape is moving fast enough that specific model names in this section will become outdated. The roles and the principle of using characteristic biases deliberately are stable; the specific model assignments should be revisited as new models emerge.

## 5.5 Hermes Agent as Reference Implementation

Hermes Agent (github.com/NousResearch/hermes-agent) by Nous Research demonstrates the right operational concepts for an autonomous agent that lives on a server and communicates across multiple platforms. It is worth studying as a reference implementation. It is not recommended as a codebase to build on.

A code review identified serious structural problems: a 1000-line main agent loop function, 11 separate hardcoded format parsers, monolithic 2700+ LOC files, if/else chains hardcoding tool names to execution logic, hardcoded SQL throughout. These are maintainability and reliability problems that become debugging nightmares in a system intended to run autonomously for months. Phosphene’s design philosophy — modular, swappable, simple interfaces — is directly at odds with this architecture.

### What to Learn from Hermes (Concept, Not Code)

- Single gateway process serving Telegram, Discord, Slack, WhatsApp simultaneously, installable as a systemd service. The concept is sound; implement cleanly with one module per platform and a simple message bus.
- Natural language cron scheduling for autonomous tasks. Maps directly onto the free play scheduler and distillation cycle triggers. Implement as a lightweight scheduler with a clean interface.
- Playwright integration for browser automation. Implement as an isolated module with a single well-defined interface to the Explorer.
- FTS5 SQLite session search with LLM summarization for conversation history. Implement as a clean module with a defined query interface.
- SOUL.md as the primary identity slot in the system prompt — the pattern is right. Our version is Tier 3 personality files, dynamically written by the distillation engine rather than user-edited.
- Honcho (plastic-labs/honcho) for cross-session user modeling. Worth investigating independently as a potential feedback enrichment layer.

### Build It Clean

Each of these is a well-defined, independently solvable problem. None are architecturally complex — the gateway is a message router, the cron is a scheduler, the browser tool is a subprocess wrapper. Building from scratch takes longer than inheriting Hermes but produces code you understand, can debug, and can extend. Given that this system is intended to run unattended for months or years, that tradeoff is strongly in favor of building clean.

## 5.6 Ouroboros as Secondary Reference

Ouroboros (github.com/joi-lab/ouroboros, github.com/razzant/ouroboros) remains useful as a pattern reference. Specific components worth examining:

- BIBLE.md / identity.md pattern: template reference for Tier 3 personality file structure
- OpenRouter-based LLM dispatch: reference for the model router

Treat as a pattern reference, not a codebase candidate.

## 5.7 Module Library: Reusability and the TGBot Connection

Phosphene is built on the same architectural principles as TGBot (the GitHub Digest Bot): clean module boundaries, typed dataclasses at every interface, no cross-dependencies except at the orchestrator level, each module defines its own exception types, tests mirror the module structure. This means the two projects form the beginning of a personal building-block library rather than two isolated codebases. Modules built to this standard are reusable across agent projects without modification.

The alternative — pulling in external frameworks — carries the risk demonstrated by Hermes Agent: surface-level capability hiding structural problems that only become visible when you need to debug or extend. Building your own modules to spec takes longer but produces code you understand completely and can trust to run unattended.

### Modules Available from TGBot

- platform_clients/telegram_client.py — Telegram Bot API client, message sending, channel posting, inline keyboards. Reusable directly; no TGBot-specific logic.
- platform_clients/telegraph_client.py — Telegraph API for long-content overflow. Reusable directly.
- platform_clients/formatting.py — MarkdownV2 escaping, message layout utilities. Reusable directly.
- storage/ — SQLite/MySQL abstraction, connection management, typed CRUD, schema migration. The schema will differ completely between projects but the infrastructure layer is reusable.
- llm_client/ — LLM provider abstraction, two-tier model routing (quality-critical vs. commodity). Extend to add subscription rotation logic.

### Modules Built for Phosphene, Reusable Elsewhere

- gateway/ — multi-platform inbound message routing (Telegram, Discord, Slack). Any agent project that needs to receive messages across platforms can use this directly.
- scheduler/ — cron-based autonomous task execution with budget tracking. Generic; reusable by any scheduled agent.
- explorer/ — Playwright subprocess, pre-fetch scoring, source evaluation protocol, subscription management with human-approval gate. Useful for any content-ingestion agent: openclaw, market intelligence, research assistant.
- attention_filter/ — LLM-based content scoring against a criteria set, annotation rather than summarization, structured fragment output. The criteria are Phosphene-specific but the scaffolding is generic. Replace criteria for domain-specific filtering.
- distillation/ — RAPTOR-style clustering, threshold-triggered synthesis, two-step reflect-evolve. Reusable for any system that needs to build hierarchical knowledge from accumulating content.

### Modules That Are Phosphene-Specific

- memory_store/ — three-tier hierarchical memory with link-density decay, personality-consistent forgetting, and unresolvedness tracking. The architecture encodes assumptions specific to personality development.
- output_router/ — see below. The routing logic encodes Phosphene’s intent-tag system and feedback coupling.
- feedback_collector/ — see below. Signal interpretation is calibrated to Phosphene’s attractor model.

## 5.8 Evaluation and Delivery Architecture

[FOUNDATIONAL] Delivery in Phosphene is structurally different from TGBot’s delivery. TGBot delivery is a pure output pipe: fixed format, fixed destination, no feedback loop, no agent choice. Phosphene’s delivery is entangled with the evaluation system and partly agent-directed. The two must be designed together.

### [FOUNDATIONAL] Evaluation Is Multi-Layered

Evaluation happens at four distinct levels, each with different mechanisms and different signals:

- Atomic note evaluation — human skims the daily log and likes notable entries. Low-friction, asymmetric (likes only), feeds back into the attention filter’s structural signal calibration. Volume is high; the mechanism must be nearly zero-friction or it won’t happen.
- First distillate evaluation — human reviews Tier 2 pattern clusters periodically. Higher effort, richer signal, about whether the synthesis is genuinely good rather than whether individual items are interesting. Appropriate cadence: weekly or when distillation runs.
- Output evaluation — free play outputs, requested outputs, weekly synthesis. Delivered through channels that carry a feedback affordance (reply thread, reaction, rating). Intent tag matters: feedback should be evaluated against what the output was trying to do.
- Reviewer panel evaluation — automated multi-model review of high-importance outputs. Logged as distinct signals by model identity. Disagreement tracked as a separate signal from consensus.

### [FOUNDATIONAL] Delivery Format Is Coupled to Feedback Affordance

For outputs where structured feedback matters, the delivery format must include the feedback mechanism, not treat it as an afterthought. Different output types warrant different delivery+feedback combinations:

- Internal notes (agent records something for itself) — no delivery, stored directly to memory.
- Daily log surfacing — a short list delivered to a private channel where likes are the feedback mechanism. Telegram inline keyboards or Discord reactions both work; the key is that the feedback action requires at most one tap.
- Provocations and questions — posted to a conversational channel (Discord thread or Telegram group) where reply is the natural feedback mechanism. The thread becomes part of the memory store.
- Long synthesis — Telegraph for the full content, a short hook message with a link. Reactions on the hook message are the feedback signal.
- Free play outputs — full reviewer panel triggered automatically. Also delivered to a channel where human engagement is invited and logged.

### [PROVISIONAL] Output Router Module

The output router sits between the Generator and the platform clients. It receives (content, intent_tag, output_mode) and decides: which platform, which format, which feedback affordance. This logic is in the generator layer, not the delivery layer.

Routing heuristics (provisional, calibrate through use):

- intent_tag = internal_note → memory store only, no delivery
- intent_tag = question, output_mode = free_play → Discord thread, reply as feedback
- intent_tag = provocation → most public available channel, reactions as feedback, reviewer panel triggered
- intent_tag = synthesis, length > 3000 chars → Telegraph + hook message
- intent_tag = log_surfacing → private Telegram channel, inline keyboard with like button
- intent_tag = subscription_proposal → direct message to human, approve/reject inline keyboard

### [PROVISIONAL] Feedback Collector Module

The feedback collector receives events from all platforms, normalizes them into a common format, and writes them to the memory store as tagged events. Key design points:

- Each feedback event carries: source_platform, output_id (links back to the output that triggered it), feedback_type (like, reply, reaction, reviewer_signal), content (for replies and reviewer signals), intent_tag of the original output.
- Intent-aware interpretation: a downvote on a deliberately provocative output is not a negative signal. The intent_tag is always passed alongside the valence.
- Reviewer signals are logged with model identity attached. Disagreement between reviewers is computed and stored as a separate field.
- The feedback collector does not interpret signals — it normalizes and stores. Interpretation happens in the distillation engine when feedback events are incorporated into the pattern layer.

## 5.9 Configurable Parameters: The Phosphene Deployment vs. the Platform

The architecture described in this document was designed with one specific deployment in mind — Phosphene, seeded from one person's corpus, oriented toward a specific kind of intellectual output. But most of the design decisions that were resolved one way could have been resolved differently. Making these decisions explicit as configurable parameters serves two purposes: it clarifies what the actual design choices were and why, and it opens the path toward the system being a reusable platform that other deployments can configure without forking the codebase.

The following parameters are organized by layer. Each entry states the current Phosphene value, the range of sensible alternatives, and what changing it would do.

A `deployment.yaml` at the root of the project sets all of these. The codebase reads from it; nothing is hardcoded into module logic.

### Attention Filter Parameters

**Filter axis weights** — a numeric weight (0.0–2.0) for each Phase 2 scoring axis plus Phase 1 precision_surplus. These are starting points for empirical calibration — expect revision after the first month of operation.

*Phosphene values:* friction=1.5, structural_insight=1.3, unexpected_connection=1.3, unresolvedness_affinity=1.2, precision_surplus=1.2 (Phase 1), liminality=1.0, link_density=1.0, cluster_novelty=0.8.

The weighting prioritizes depth and challenge over novelty: friction is highest because it challenges existing structure without dissolving it. Structural insight and unexpected connection are next — depth of synthesis and bridge-building. Liminality and cluster novelty are at or below baseline — they capture gap-filling and new territory, which is useful as a tiebreaker but risks novelty addiction if dominant (see ARCH_attention_filter.md, Phase 2 risk note). Cluster novelty is the lowest because pure "beyond everything" novelty is the weakest signal for personality development.

*What changing it does:* a deployment for a scientist would upweight structural_insight and precision_surplus. A cultural critic deployment would upweight liminality and unexpected_connection. A contrarian deployment might invert the friction axis — seeking smooth consensus specifically to challenge it. These weights are the highest-leverage parameter in the system because they shape everything that enters the memory store.

**Prompt-to-structure transition threshold** — the network density metric (mean link degree, note count, or cluster count) at which the filter begins weighting structural signals over explicit criteria.

*Phosphene value:* TBD — first-month calibration task. Start prompt-weighted; begin monitoring density metrics from day one.

*What changing it does:* a lower threshold produces faster structural self-organization, risking premature convergence. A higher threshold keeps the personality closer to the explicit criteria for longer, risking rigidity.

### Memory Store Parameters

**Tier 1 retention window** — how many days raw annotated fragments are retained before archiving or requiring promotion.

*Phosphene value:* 30 days.

*Range:* 7 days (fast-cycling, prioritizes recency) to 90 days (slow accumulation before pruning).

**Tier 2 synthesis cadence** — how frequently the pattern layer is synthesized from Tier 1.

*Phosphene value:* weekly.

*Range:* daily (rapid pattern formation, noisier) to monthly (slower, more conservative synthesis).

**Tier 3 distillation cadence** — how frequently personality files are proposed for update.

*Phosphene value:* monthly.

*Range:* weekly (fast personality development, higher drift risk) to quarterly (stable, slower to develop).

**Compression safety cap** — maximum fraction of a tier that can be pruned in a single distillation pass.

*Phosphene value:* 50%.

*What changing it does:* lower cap produces slower, more conservative compression. Higher cap allows more aggressive pruning, which accelerates development but risks losing material that would have been valuable later.

### Inertia and Drift Parameters

**Version-count inertia per cycle** (`inertia_per_cycle`) — how much additional resistance a personality file gains per surviving T2→T3 distillation cycle. Effective weight = `min(max_inertia, 1.0 + (version_count - 1) * inertia_per_cycle)`.

*Phosphene value:* TBD — calibrate empirically after the first T2→T3 cycles.

*Range:* 0.0 (no inertia; all personality files equally revisable regardless of age) to 1.0 (rapid stabilization; files become hard to revise after a few cycles).

*What changing it does:* lower values produce a system that remains fluid longer. Higher values produce one that locks in early patterns. A deployment without strong seed material would use lower inertia to allow more development.

**Maximum inertia cap** (`max_inertia`) — ceiling on how much resistance any personality file can accumulate.

*Phosphene value:* TBD — likely 3.0–5.0 range.

*What changing it does:* prevents any personality file from becoming permanently immutable. Even the most established claims can be revised if enough evidence accumulates.

**Corpus sources** — the writing archive(s) ingested through Source Ingestion corpus adapters during the bootstrap phase.

*Phosphene value:* LiveJournal archive (primary — highest personality signal, ingested via `corpus_livejournal` adapter), Twitter export (secondary — processed as linked-article graph with reactions as annotations, via `corpus_twitter`), blog posts (tertiary — more curated, underrepresents tensions, via `corpus_blog`), Claude conversation history (secondary — highest signal for intellectual moves, via `corpus_conversations`).

*What changing it does:* a deployment with no long-form writing archive would weight conversation history and shorter-form material more heavily. A deployment seeded from academic writing would produce different initial associative networks than one seeded from personal journaling.

### Free Play Parameters

**Free play frequency** — how often the unstructured impulse fires when tension threshold is not met.

*Phosphene value:* weekly floor (tension threshold may trigger more frequently).

*Range:* daily (high autonomy, high output volume) to never (fully reactive system, no unsolicited outputs).

**Tension threshold** — the accumulated unresolved tension score that triggers a free play session ahead of schedule.

*Phosphene value:* TBD — calibrate empirically after the first month of operation.

**Proactive budget** — maximum proactive messages per budget window (following KAIROS pattern).

*Phosphene value:* 2 per 15-minute window, reactive messages unrestricted.

*What changing it does:* higher budget produces a more talkative, initiating system. A deployment intended as a background system with occasional surfacing would set this to 1 or 0.

**Affordances list** — which output modes are available during free play.

*Phosphene value:* post to Discord, send Telegram message, write draft essay, propose source subscription, request conversation with human, generate internal note.

*What changing it does:* a deployment with Substack integration would add "publish draft." A deployment without Discord would remove that affordance. The affordances list defines the shape of initiative — what the system can spontaneously do constrains what kind of personality can emerge.

### Reviewer Panel Parameters

**Panel composition** — which models serve as reviewers and in which roles.

*Phosphene value:* adversarial reviewer (separate invocation, any capable model), Claude (structural coherence), Gemini (factual grounding), Grok (adversarial external reader), GPT (accessibility). All provisional; revisit as model landscape evolves.

**Panel trigger policy** — which output types receive automated review.

*Phosphene value:* free play outputs → full panel; high-importance prompted outputs → two or three reviewers; routine outputs → none.

*What changing it does:* a deployment oriented toward public writing would run the full panel on all outputs before publication. A private journaling deployment would disable automated review entirely and rely solely on human evaluation.

### Output and Delivery Parameters

**Platform set** — which platforms the gateway connects to.

*Phosphene value:* Telegram (primary control interface), Discord (primary output channel), Telegraph (long-form overflow).

*What changing it does:* a deployment oriented toward public output would add Bluesky or Mastodon via Publora. A deployment for internal use only might use only Telegram.

**Intent tag routing table** — the mapping from (intent_tag, output_mode) to (platform, format, feedback_affordance).

*Phosphene value:* see Section 5.8 routing heuristics.

*What changing it does:* a deployment where all outputs go to one channel collapses the routing table to a single entry. A deployment with richer platform set expands it.

### A Note on Specificity

The parameters above are where the personality actually lives in the architecture — more than in the seed document and more than in the module structure. Two deployments with different attention filter weights, different compression ratios, different inertia settings, different source profiles, and different affordances lists would develop in genuinely divergent directions even from similar seeds. The architecture is the chassis; the deployment configuration is what makes it a particular vehicle.

This also means the attention filter axis weights deserve more careful specification than "friction, unexpected connection, precision surplus." For Phosphene specifically, these should be operationalized from the seed corpus at a level of specificity that a different person's corpus couldn't satisfy equally well. "Friction" is too broad. The specific *kinds* of friction that appear in the seed — where precision meets imprecision, where synthesis refuses to flatten, where the executor's eye meets the theorist's frame — are the actual parameters. The generic labels are placeholders for values that should be derived from the seeding process itself.


# 6. Open Questions and Further Development

## 6.1 Identified Gaps

### Spontaneity Mechanism

The original framing ("the hunger problem") asked: can the system generate forward momentum from internal state without external prompting? The reframing (Section 1.5) clarifies that for a discontinuous system, the question is different: **when activated, how much freedom does the system have to deviate from the stated purpose of the activation?** The architectural response — a per-activation free-play budget plus tension-responsive scheduling — is specified as a principle (Section 4.5) but not yet as an implementation. Key calibration questions: what is the right size for the lateral-movement budget (too small and deviation never happens; too large and scheduled tasks don't complete)? How should unresolved tension be quantified to drive scheduling frequency? These are first-month calibration tasks once the memory store and distillation engine are operational.

### The Prompt-to-Structure Transition

The attention filter starts prompt-weighted and shifts toward structure-weighted as network density develops. The transition mechanism is internal to the filter module and does not affect its external interface (see Section 3.4, Architectural Note). The remaining questions — what density metric best drives the crossover (note count, mean link degree, cluster count, or a composite), what the weighting function looks like (linear, sigmoid, stepped), and where the crossover sits — are empirical calibration tasks for the first month of operation once the memory store and attention filter are both running on real content.

### The Third-Order Distillation Question

Whether three-tier distillation produces genuine insight or progressive banality is an empirical question that cannot be answered in advance. The architecture is designed to test it, but the answer requires running the system. The “stopped reading” failure signal should be monitored specifically for signs of increasing abstraction without increasing insight.

### Multi-Model Reviewer Panel Calibration

Section 5.4 proposes a multi-model reviewer panel with assigned roles. The key unresolved question is not whether to use such a panel but how to calibrate it: which model’s signals to weight most heavily, how to handle systematic disagreement between reviewers, and how to prevent any single reviewer’s biases from dominating personality development over time. The panel is part of the enclosure — its composition is a design choice with long-term consequences that will only become visible after months of operation.

## 6.2 Unexplored Options

- Embodied input: the system currently processes only text. Adding image or audio sources would change the character of what gets ingested and potentially the character of what gets generated.
- Temporal memory: the Zep framework offers a temporal knowledge graph architecture that tracks how beliefs change over time. This could be useful for tracking personality development explicitly, not just implicitly.
- Adversarial self: a second agent instantiated from the same seed but given a divergent prompt (e.g., “be skeptical of everything the primary agent says”) could provide internal friction that prevents the primary agent from converging too quickly on a stable attractor.
- Publication: the system currently outputs to Discord and Telegram. A Substack or public blog would change the feedback dynamics — the agent would receive responses from people with no relationship to the project, which is a different kind of selection pressure.
- Corpus update: the seed corpus is fixed at initialization. Periodically re-seeding from new writing by the human would allow the system’s personality to track the human’s actual development rather than diverging from it permanently.

## 6.3 Development Sequence

Suggested order of implementation. Each step is a standalone module with a defined interface; earlier steps do not need to be complete before later steps can be prototyped in parallel.

    7. Build three-tier memory store — the architecture everything else depends on
    8. Write and manually calibrate the attention filter prompt — test on a small sample before automating
    9. Build source ingestion adapters — corpus adapters first (bootstrap), then live channel adapters
    10. Build gateway module (Telegram + Discord) — one module per platform, simple message bus. Reference: Hermes concepts.
    11. Discord output and basic prompted generation
    12. Distillation engine (Tier 1 → Tier 2 first, then Tier 2 → Tier 3 with two-step reflect-evolve)
    13. Feedback collection and daily log review
    14. Explorer module (link-following and subscription proposals) — Playwright subprocess, isolated interface
    15. Free play — only after sufficient accumulated unresolved tension, using Hermes's cron and gateway for delivery

# 7. External Review and Design Responses

*This section records the outcomes of an external review conducted May 2026, after Modules 1–6 were complete (Memory Store, Attention Filter, Source Ingestion, Gateway, Generator + Output Router, Distillation). The review identified nine areas for improvement. Each is documented below with the design response, rationale, and architectural placement.*

*The reviewer's compressed critique: "The spec is now good enough that its main risk is not under-specification, but elegant over-resolution of phenomena that should remain partly rough." The three questions posed: (1) what is the smallest build that can falsify the core thesis? (2) which internal scores deserve first-class status? (3) how do you keep the formalization from sterilizing the attractor?*

## 7.1 Claim-Centric Identity Layer

**Review observation:** Personality files carry version-count inertia at the file level, but files are containers — a file with five statements of different quality gets uniform protection. Moving to per-claim evidence accounting (support, contradiction, recency, source diversity, confidence) would fit the skeptical memory principle better.

**Design response: No change.** "Claim" implies propositional content with clear boundaries. The material this system processes — liminal observations, aesthetic responses, unresolved tensions — does not decompose cleanly into typed claims. The personality files contain nebulous, associative material where the unit of meaning is not a statement but a constellation of related tensions. File-level inertia is coarser but honest about the granularity of what is actually being stored. Version-count inertia remains the drift mitigation mechanism.

The two-step reflect-evolve distillation (Section 3.6) already makes claim-level judgments during the evolution pass — it just doesn't store them at that granularity. If experience shows that file-level inertia is too coarse (specific failure: mature files retaining stale observations alongside still-valid ones, where the stale observations resist revision because the file as a whole has high inertia), the claim-level approach can be revisited.

## 7.2 Centroid-Heaviness in Geometric Scoring

**Review observation:** Liminality, friction, and unexpected connection are all scored against cluster centroids (Section 3.3a). Centroids are compressive — they erase local weirdness, minority subthreads, and the anomalies that often matter most. The spec says it wants friction-preserving behavior; centroid logic rewards smooth cluster-level structure.

**Design response: Observe before fixing.** Two candidate fixes were identified — bridge-node scoring against high-link notes (comparing incoming content against specific structurally important notes rather than centroids), and outlier persistence tracking (detecting items repeatedly near a cluster but never assimilated into its summary). Both are valid but premature — they are solutions to a hypothetical problem.

The correct first step is diagnostics. Build network health instrumentation (Section 7.7) that measures whether centroid-heaviness is actually erasing anomalies in practice. If diagnostics confirm the problem (outlier ratio declining while cluster count grows, bridge-node density stagnating as note count rises), implement the fixes then.

No module contract changes required — the diagnostic tool reads from Memory Store's existing API surface.

**Promote-when:** Diagnostics show centroid-heaviness erasing anomalies.

## 7.3 Unresolvedness as First-Class Composite Score

**Review observation:** Unresolvedness drives free play, lateral movement, scheduling, and generative tension (Sections 1.5, 4.5), but compared with the formalized geometric criteria (Section 3.3a), it reads more like an honored concept than an operationalized metric.

**Design response: Formalize as composite.** Define unresolvedness explicitly as a composite signal with measurable subcomponents:

- **Repeated reappearance:** content similar to existing notes reappears in new ingestion batches without the original being promoted or resolved. Detected by the Attention Filter during `search_by_embedding` — incoming content with high similarity to notes that already have high unresolvedness is a signal that the thread keeps surfacing.
- **Rising link count without promotion:** note has accumulated significant connections but remains in Tier 1 — well-connected but not yet synthesized. Computed from Memory Store data: `link_count` vs. `tier`.
- **Conflicting alignments:** note has connections to notes that themselves are in tension (friction targets pointing at each other, or connected notes with high mutual unresolvedness). Detectable during Distillation when reading cluster members.
- **Engagement without synthesis closure:** note received positive feedback (human found it interesting) but has not been promoted through distillation. Computed by the Feedback Collector when feedback events exist on notes still in Tier 1.
- **Survival across distillation cycles:** note has persisted through one or more `distill_t1_to_t2` runs without being clustered — it keeps surviving decay but doesn't fit any cluster. Computed by the Distillation engine from run metadata.

The composite formula is defined as a shared utility. Each module updates the unresolvedness score at its natural touchpoint:

- **Attention Filter** sets the initial value at ingestion (already does this).
- **Distillation** updates during `distill_t1_to_t2` based on survival, link-growth-without-promotion, and conflicting alignment signals.
- **Feedback Collector** adjusts when engaged-but-not-promoted notes receive positive feedback.

The Memory Store contract does not change — `unresolvedness` is already a `float` on `NoteInput` and `MemoryNote`, and `update_note()` accepts updated values. `DensityMetrics` already exposes `unresolved_count` and `max_unresolvedness`.

## 7.4 Feedback Anti-Overfitting

**Review observation:** The feedback-closes-on-structural-features design (Section 3.8) is strong, but the most available human signals — likes, replies, continued reading — are biased toward immediacy, legibility, and present mood. A system can become more engaging while becoming less deep. The "stopped reading" failure signal is very blunt.

**Design response: Four anti-overfitting mechanisms across three modules.**

### Wild-Card Accepts (Attention Filter)

A configurable fraction of below-threshold items are accepted despite scoring below `acceptance_threshold`. Tagged with `retention_criteria=["wild_card"]`. This maintains a zone of content that enters the memory store without being shaped by the current feedback-calibrated scoring. The wild-card budget is immune to criteria weight adjustments — it is a random exploration channel that feedback cannot close.

Config: `wild_card_ratio: float = 0.05` on `AttentionFilterConfig`. During `filter_content`, 5% of below-threshold items are randomly admitted with full annotation. The ratio is deliberately small — large enough to maintain genuine diversity, small enough not to dilute the filter's personality-shaping function.

### Near-Discard Recording (Attention Filter)

Items that score within a configurable margin below `acceptance_threshold` (e.g., within 0.05 below) are recorded as near-misses in `FilterResult`. This creates a pool of "things the filter almost kept" available for periodic human review, calibrating the filter against the failure mode you cannot normally see: interesting content filtered out before anyone could evaluate it.

Config: `near_miss_margin: float = 0.05` on `AttentionFilterConfig`. Output: `near_misses: list[AnnotatedFragment]` on `FilterResult`.

### Temporal Engagement Distinction (Feedback Collector)

Distinguish between immediate engagement (liked/replied within hours) and durable engagement (still referenced, re-engaged, or built upon days later). Current feedback captures immediate engagement only. A delayed re-check after a configurable window (e.g., 7 days) evaluates whether the engagement persisted: did the note's connections grow? Was it referenced in generated output? Did the human re-engage? If so, record a `"delayed_positive"` signal with higher importance than the immediate like.

This separates "interesting right now" from "still seems important later" — a distinction the original feedback design acknowledges as important (Section 3.8: "what the system should become" vs. "what current-you taps") but does not operationalize.

### Periodic Resurfacing (Orchestrator)

During `decay` activations, query for notes with high `link_count` but zero feedback events — structurally important material the human has never engaged with. Surface a small sample via Gateway. This counteracts the feedback loop's tendency to let structurally important but un-engaged material fade. The selection is weighted toward notes with high unresolvedness × link density, consistent with the lateral-movement priority function (Section 1.5).

## 7.5 MVP Profile and Phased Complexity

**Review observation:** The `deployment.yaml` parameterization (Section 5.9) creates too many interacting knobs before a minimal organism exists. Too many live dials make early behavior impossible to interpret.

**Design response: Define a brutally small MVP profile.** A minimal operational loop that can run before Modules 7–9 are built:

- **Sources:** 1 corpus adapter + 1 live channel (Telegram or RSS)
- **Output:** 1 channel (Telegram only)
- **Scoring:** Phase 1 only (prompt-weighted, no Phase 2 geometric scoring)
- **Distillation:** T1→T2→T3, with manual human review of Tier 2 clusters before any T2→T3 run
- **Free play:** Fixed budget, no tension-responsive scheduling
- **Reviewer panel:** None
- **Feedback:** None (manual observation only)
- **Explorer:** None

This is a sequential script (`run_mvp.py`), not the full Orchestrator. It runs each step in order, pausing for human review at the T2 stage. The goal is to answer the core falsification question — does three-tier distillation produce genuine personality development or progressive banality? — with the smallest possible build.

Complexity is added one module at a time after the MVP demonstrates the core thesis. The spec describes a platform and a deployment simultaneously; the MVP forces a hard separation. The platform is the module library; the MVP is the first deployment.

## 7.6 Free-Play Task Arbitration

**Review observation:** "Every activation carries a free-play budget" (Section 4.5) is conceptually strong, but in practice this is where autonomous systems get annoying or unstable. When exactly does the system get to defect from scheduled work into free play? The philosophy is clear; the scheduler policy is not.

**Design response: Explicit arbitration rules in the Orchestrator contract.** Four mechanisms prevent "everything interesting cannibalizes everything necessary":

### Minimum Completion Fraction

The scheduled task must report completion of at least `min_task_completion` (default 80%) before the lateral check fires. This prevents chronic task abandonment. Ingestion reports completion as fraction of source items processed; generation reports completion as output produced; distillation is non-interruptible.

### Preemption Classes

Activation types are classified as preemptible or non-preemptible. Non-preemptible tasks (`distillation_t1t2`, `distillation_t2t3`, `respond`, `decay`) run to completion regardless of lateral opportunity. Preemptible tasks (`ingestion`, `generation`, `explore`) allow lateral diversion after `min_task_completion`.

### Debt Accounting

If lateral movement exceeds its allocated budget, the overage is deducted from the next activation's base budget. Lateral movement cannot borrow indefinitely — accumulated debt reduces future base budgets until repaid. Maximum debt is capped to prevent runaway depletion.

### Cool-Down Windows

Minimum time between lateral outputs prevents free-play-induced cascades where one self-initiated output triggers lateral movement in the next activation. Default: 2 hours.

## 7.7 Failure-Mode Instrumentation

**Review observation:** The spec describes failure modes conceptually — mirrorhood, stagnation, novelty addiction, drift, overcompression — but does not monitor them operationally. Many are described as possibilities rather than measured conditions.

**Design response: Standalone diagnostic tooling.** A `tools/network_diagnostics.py` script that reads Memory Store's existing API and computes health metrics. This is not a core module — it has no ARCH file, no contract, no dependency. It is a diagnostic instrument run on demand or on a cron schedule, producing a human-readable report.

| Metric | What it measures | Source |
|--------|-----------------|--------|
| Mirror index | Lexical/style overlap with seed corpus | Mean embedding distance between recent outputs and seed notes |
| Premature convergence | Cluster diversity collapse | Inter-cluster distance trend; cluster count vs. note count ratio |
| Novelty addiction | Accepted novelty rising, engagement falling | Cluster novelty on accepted items correlated with feedback rates |
| Compression damage | Over-aggressive forgetting | Decayed notes later referenced by surviving notes (orphaned links) |
| Free-play value ratio | Self-initiated output quality | Proportion of lateral outputs whose source notes appear in Tier 2 clusters |
| Outlier ratio | Anomaly survival | Notes with similarity < 0.3 to nearest centroid |
| Bridge-node density | Connective tissue formation | Notes with similarity > 0.4 to 2+ distant clusters |
| RAPTOR-Louvain divergence | Structural vs. semantic clustering gap | Louvain community detection on the link graph compared against RAPTOR embedding clusters — notes whose structural community differs from their content cluster are bridge notes the centroid-based scoring may miss |
| Unresolvedness distribution | Tension health | Histogram of unresolvedness scores |

These metrics serve two purposes: (1) early warning for the failure modes identified in Section 6.1, and (2) evidence base for deciding whether the centroid-heaviness fixes (Section 7.2) are needed. The diagnostics are built before Module 7 so that baseline measurements exist before feedback starts flowing into the system.

## 7.8 Reviewer Panel as Diagnosis, Not Approval (Deferred)

**Review observation:** Multi-model review (Section 5.4) can sand down exactly the eccentricity the system is meant to cultivate. A cultivated organism can get domesticated by its critics.

**Design response: Document and defer.** When the Reviewer Panel is promoted from deferred status and given an ARCH file, the panel should be designed as an annotation system, not a gate. Reviewers annotate tensions — "likely confusing but fertile," "clear but flattening," "factually risky," "stylistically generic" — rather than producing a composite quality score. Reviewer output is stored as tagged annotations on the generated content, consumed by Distillation as structural metadata, not as pass/fail signals blocking output delivery.

The panel should never block delivery. It annotates after delivery, not before.

**Promote-when:** Generator outputs are landing on real channels and a single-model evaluation signal is insufficient.

## 7.9 "Interesting System" vs. "Interesting Writer" (Deferred)

**Review observation:** A sophisticated exploration machine can still produce outputs that are mostly interesting because the architecture is interesting. The system may generate visibly agentic artifacts rather than genuinely compelling thought.

**Design response: Recurring human audit question and partial operationalization.** The audit question — "Did this output feel like a report from a real internal exploration, or like a clever byproduct of the machinery?" — resists formalization but protects the project's center. It should be asked regularly once outputs are flowing.

One partial operationalization: track whether generated outputs reference specific accumulated material (notes, tensions, unresolved threads) or speak in generalities. Outputs grounded in specific internal history are more likely genuine explorations; outputs that could have been generated from personality files alone without referencing specific memory are more likely machinery artifacts. This metric can be added to `tools/network_diagnostics.py` once Generator output logs exist.

**Promote-when:** Generator outputs are being produced regularly and human evaluation is active.

# Appendix A: Corpus-to-Knowledge-Graph Technique (Reference)

*This technique was originally planned as Phosphene's seeding pipeline. It was superseded by D-13 (corpus ingestion through Source Ingestion adapters, personality development exclusively through Distillation). The technique itself remains a useful tool for corpus analysis, diagnostics, or future applications.*

## MiroFish Pipeline

MiroFish (github.com/666ghj/MiroFish) is a corpus-to-knowledge-graph-to-personality engine. Its pipeline:

1. Document(s) → LLM ontology extraction → knowledge graph (KuzuDB by default, Neo4j in the offline fork)
2. Knowledge graph → entity and relationship filtering → agent persona generation via LLM
3. Persona generation produces: personality traits, background, stance, social relationships, initial memory

The offline fork (github.com/nikmcfly/MiroFish-Offline) runs entirely locally with Neo4j + Ollama, fits the Pi 5 architecture, and has an English UI. The graph construction layer is reusable; the OASIS simulation engine is not needed.

## Potential Future Uses

- **Diagnostic analysis**: run the pipeline on the accumulated memory store at any point to produce a knowledge graph snapshot — useful for visualizing the associative network's structure and identifying blind spots or over-connected clusters.
- **Corpus comparison**: run the pipeline on the original seed corpus and on a later snapshot of the personality's outputs to visualize how the associative structure has diverged from the seed.
- **Cross-corpus structural patterns**: if incremental Distillation proves unable to find structural patterns that span widely separated corpus sources (the D-13 revisit-if condition), a batch knowledge graph run could serve as a supplementary analysis step.
- **New deployment seeding**: if the platform is used for additional deployments with different seed corpora, the batch pipeline might be more appropriate for a different deployment's needs even though it was superseded for Phosphene's.
